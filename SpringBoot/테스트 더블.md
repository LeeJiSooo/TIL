## 가져가야 할 핵심

- 테스트 더블이 무엇이고 왜 쓰는지?(왜 테스트에서 외부 의존성 격리가 필요한지)
    - 테스트 대상이 의존하는 실체 객체를 대신하는 가짜 객체
- 가짜 객체의 종류가 있는데 이 종류 들에 대해서 알기 → 그 중에서 stub이랑 mock의 차이점 → 상태 검증과 행위 검증의 차이

## 테스트 더블의 정의와 필요성

- 테스트 대상 코드가 의존하고 있는 실제 객체를 대신하여 사용 되는 모든 종류의 가짜 객체를 통칭하는 용어이다.
    - SUT(System Under Test) : 현재 진짜 검증하고자 하는 테스트 대상(ex. 주문, 회원가입, 글쓰기 등)
    - 의존 객체 : SUT가 제 기능을 하기 위해 호출하는 외부 객체(ex. Repository, 외부 결제 모듈, 이메일 클라이언트 등)
- 존재 이유(외부 의존성 격리) : 우리가 작성하는 비즈니스 로직은 단독으로 돌지 않고, DB에 값을 넣고 토스페이먼츠 같은 외부 결제 API를 부르고, 메일 서버를 통한다.
    
    만약 테스트 코드에서 이 실제 의존성들을 그대로 사용하면 네트워크 지연, DB상태, 외부 서버 장애에 노출된다.
    
    → 좋은 테스트의 규칙인 F(Fast), R(Repeatable), I(Independent)가 무너진다.
    
    → 외부 결제 API 서버가 터졌을 때 “우리 시스템이 예외 처리를 안전하게 진행하는가?”를 테스트하고 싶어도 외부 서버 상태를 마음대로 조작할 수 없다.
    
    → 실제 의존 객체와 똑같이 생긴 테스트 더블을 설계에 넣어서, 외부 환경과 완전히 격리된 채 빠르고 안정적인 테스트 환경을 구축할 수 있다.
    

## 상태 검증 - 스텁(Stub)

- 호출 되었을 때 미리 준비된 고정된 정해진 값만 돌려주는 가짜 객체이다.
- **언제쓰는가** : SUT가 의존 객체로부터 어떤 결과값(조회 데이터, 결제 성공 여부 등)을 받아와서 그 값을 토대로 비즈니스 로직을 수행할 때 사용한다.
- 의존 객체가 내부적으로 어떻게 돌았는지가 아니다.
    
    의존 객체가 어떤 값을 넘겨주었을 때, 우리 SUT(테스트 대상)가 올바른 판단을 내리는가?가 유일한 관심이다.
    
- **검증 방식** : **상태검증** → 최종 결과가 우리가 기대한 값과 같은지 `assertEquals`, `assertTrue` 등으로 검증한다.

```java
// 테스트 대상 (SUT)
public class CouponValidator {
    private final CouponRepository couponRepository;

    public CouponValidator(CouponRepository couponRepository) {
        this.couponRepository = couponRepository;
    }

    // 쿠폰이 존재하고 만료되지 않았는지 검증
    public boolean isValid(String couponId) {
        Optional<Coupon> couponOpt = couponRepository.findById(couponId);
        if (couponOpt.isEmpty()) {
            return false;
        }
        return !couponOpt.get().isExpired();
    }
}
```

→ 쿠폰이 유효한지 검증하는 벨리데이터 클래스

→ 쿠폰이 유효한지 따지려면 우선 쿠폰이 저장되어 있는 곳에서 쿠폰 정보를 가져와야 한다.

→ 테스트 대상은 쿠폰 벨리데이터고 의존성은 리포지토리(디비)

```java
@ExtendWith(MockitoExtension.class)
class CouponValidatorTest {

    @InjectMocks
    private CouponValidator couponValidator;   // 테스트 대상 (SUT)

    @Mock
    private CouponRepository couponRepository;  // Stub으로 활용할 가짜 객체

    @Test
    @DisplayName("만료되지 않은 쿠폰은 유효해야 한다")
    void validCouponTest() {
        // [Given] 준비: repository의 findById가 호출되면 실제 DB에 가지 않고 만료되지 않은 가짜 쿠폰을 리턴하도록 Stub 설정
        String couponId = "VALID_COUPON";
        Coupon unexpiredCoupon = new Coupon(couponId, false); // 만료되지 않음(false)
        
        // "이 메소드가 호출되면 이 값을 반환해라" 하고 정해진 답을 세팅하는 과정
        when(couponRepository.findById(couponId)).thenReturn(Optional.of(unexpiredCoupon));

        // [When] 실행
        boolean result = couponValidator.isValid(couponId);

        // [Then] 검증: SUT가 리턴한 최종 '상태(값)'를 확인
        assertTrue(result);
    }
}
```

준비 단계에서 만료되지 않은 쿠폰을 만들고

`when(couponRepository.findById(couponId)).thenReturn(Optional.of(unexpiredCoupon));` 

→ couponRepository에서 findById가 이 쿠폰 아이디로 호출되면 만료되지 않은 쿠폰을 돌려주라고 설정을 하는 것이다. 

→ 실제 DB에 가서 쿠폰을 찾는 게 아니라 저장소가 우리가 원한 답을 한다고 가정한다.

→ 쿠폰repo가 가짜 객체로 만들어서 couponvalidator에 끼워지고 stub을 코드로 설정한다.

**이 테스트에서 확인하는 게 무엇인가?**

여기서 확인하려고 하는건 DB가 제대로 호출됐는지가 아니고 테스트 대상의 최종 상태를 확인하는 것이다. 

→ 결과 상태를 검증하는 방식을 상태 검증이라고 부르고, 이때 저장소가 stub역할을 했다.

**이 테스트가 실패한다면 뭘 의심해야하는가?**

저장소는 정상적으로 쿠폰을 반환해줬으니까 isValid의 판단 로직에 문제가 있나?를 확인해야한다.

→ 의존성을 stub으로 고정해둬서 실패의 원인이 테스트 코드 안쪽으로 좁혀지는 의미가 있다.

## 행위 검증 : 모크(Mock)

- 테스트 대상이 의존 객체의 특정 메서드를 올바른 인자와 함께 정확한 횟수만큼 호출했는지를 감시하는 감시자 객체이다.
- **언제 쓰는가** : 테스트 대상(SUT)이 로직을 수행한 뒤 의존 객체의 메서드를 제대로 불렀는지 ‘호출부 자체’가 핵심일 때 사용한다. 주로 반환값이 없어서 상태를 비교할 수 없을 때 유용하다.
- SUT가 리턴하는 결과값보다는 “외부 의존 객체와 어떤 상호작용(어떤 메서드를 몇 번 호출했는가)을 잘 마쳤는가?”를 확인하는 게 목표다.
- **검증방식** : **행위 검증** → Mockito의 verify()구문을 통해 호출 행위 자체를 확인한다.

```java
// 테스트 대상 (SUT)
public class UserService {
    private final EmailClient emailClient;

    public UserService(EmailClient emailClient) {
        this.emailClient = emailClient;
    }

		// registerUser는 반환값이 없고 void
    public void registerUser(String emailAddress) {
        // ... 사용자 등록 로직 ...
        emailClient.sendWelcomeEmail(emailAddress); // 환영 이메일 발송
    }
}
```

회원가입을 하면 환영 이메일을 보내는 UserService, 이메일 발송을 EmailClient라는 의존 객체가 담당하고 있따.

→ 반환값이 없다는 것은 stub예시처럼 마지막에 결과를 비교할게 없다는 뜻이다.

→ 그럼 이 기능이 제대로 동작했는지는 어떻게 확인하는가?

→ 환영 이메일이 실제로 보내졌는가? sendWelcomeEmail이 호출되었는가?를 확인해야한다.

```java
@Test
@DisplayName("사용자 등록 시 환영 이메일을 보내야 한다")
void sendWelcomeEmailOnRegisterTest() {
    // [Given] 준비
    String userEmail = "test@example.com";

    // [When] 실행: 회원가입 로직 작동 (반환값 void)
    userService.registerUser(userEmail);

    // [Then] 검증: 유저 정보가 등록될 때 emailClient의 sendWelcomeEmail 메소드가 
    // 해당 이메일 주소를 인자로 받아서 정확히 딱 '1번(times(1))' 호출되었는지 행위를 감시 및 검증
    verify(emailClient, times(1)).sendWelcomeEmail(userEmail);
}
```

verify는 emailClient의 sendWelcomeEmail이 해당 이메일 주소라는 인자로 정확히 한 번 호출됐는지 확인하는 구문이다.

→ 행위 검증. 테스트 대상이 돌려준 결과가 아니라 의존 객체와 어떻게 상호작용 했는가?를 본다.

→ 호출 여부를 감시하는 데 쓰인 이메일 클라이언트가 Mock역할을 했다.

## stub과 mock의 차이

검증의 시선이 다르다.

→ **stub**은 그냥 단순히 우리가 정해진 답변만 하는 역할이다.

테스트는 그 답변을 듣고 테스트 대상이 올바른 판단을 내리는지 확인한다.

→ **mock**은 테스트 대상이 특정 메서드를 제대로 호출했는지 감시한다.

답변의 내용 자체를 확인하는 것보다 테스트 대상이 외부 객체에 정확하게 메서드를 호출했는가를 확인한다.

| **구분** | **스텁 (Stub)** | **모크 (Mock)** |
| --- | --- | --- |
| **핵심 역할** | 테스트가 올바르게 굴러가도록 환경과 **정해진 답을 제공**하는 역할 | SUT가 의존 객체를 올바르게 호출하는지 **감시하고 확인**하는 역할 |
| **검증 방식** | **상태 검증 (State Verification)** | **행위 검증 (Behavior Verification)** |
| **대상** | SUT가 반환하는 **최종 결과값(상태)** | 의존 객체와의 **상호작용(호출 여부, 횟수, 인자)** |
| **대표 구문** | `when(...).thenReturn(...)` | `verify(..., times(n)).method(...)` |

## Mock을 지나치게 많이 쓰면 생기는 일

모든 걸 다 감시하겠다고 verify()를 사용하여 과도하게 Mock 위주로 테스트를 짜면 안된다.

1. 내부 구현 방식에 종속됨 : 기능의 최종 결과는 똑같은데 성능 개선이나 코드 가독성을 위해 내부 로직 순서를 바꾸거나 리팩토링을 하면, 의존 객체를 호출하는 세부 방식이 조금만 달라져도 테스트 코드가 깨져버린다.
2. 리팩토링 안전망 파괴 : 좋은 테스트 코드는 기능 개선을 안심하고 할 수 있어야 하는데, mock중심의 테스트는 리팩토링할 때마다 기능은 정상인데도 테스트 설정 코드를 전부 고쳐야 하는 생산성 저하를 일으킨다. 
    
    → 테스트가 무엇을 하는지가 아니라 어떻게 하는지를 검증해 버렸기 때문
    

→ 진짜 격리가 필요한 외부 의존성(메일 발송, 외부 결제 등)에만 최소한으로 행위 검증을 적용하고, 대부분의 단위 테스트는 스텁을 활용한 상태 검증을 중심으로 작성하는게 좋다. 

→ 객체들 간의 진짜 유기적인 결합은 단위 테스트가 아니라 통합 테스트 계층에서 한 번에 묶어서 검증하는 게 좋다.

## 정리

- 테스트 더블 : 외부 의존성(DB, API 등)때문에 테스트의 FRI 원칙을 깨지는 것을 막기 위해 실제 객체 대신 투입하는 가짜 객체를 통칭하는 말
- Stub(상태 검증) : 예측 가능한 답을 던져주는 대역이다. SUT의 최종 반환값과 상태를 검증할 때 사용한다.
- Mock(행위 검증) : 메서드 호출을 추적하는 감시자이다. 의존 객체와의 상호작용 및 메서드 호출 횟수/인자를 검증할 때 사용한다.
- 과도한 행위검증(Mock)은 구현 세부사항에 테스트를 결합시켜 리팩터링을 방해하므로, 실제로는 상태검증 기반의 설계를 지향한다.
