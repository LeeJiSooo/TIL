## RDS의 정의

클라우드에서 관계형 데이터베이스를 손쉽게 생성, 운영, 확장할 수 있도록 지원하는 AWS 완전관리형 서비스이다.

- 달리지지 않는 것(개발자 몫)
    - SQL 쿼리 작성, 테이블 설계, 인덱스 최적화, 트랜잭션 관리는 원래대로 개발자가 직접 해야한다.
- 달라지는 것(AWS위임 - 완전관리형의 본질)
    - 운영체제 및 DB 엔진 설치, 보안 패치, 자동 백업 및 스냅샷 생성, 디스크 용량 자동 확장, 장애 시 자동 복구 등 번거롭고 위험한 DB 운영/유지보수 책임을 AWS에게 위임한다.

## 왜 EC2에 직접 DB를 깔지 않고 RDS를 쓸까?

EC2에 직접 MySQL을 띄워서 쓰면 처음 1~3달은 잘 가는 것 같지만, 시간이 지날수록 개발자에게 관리 부담이 쏠리게 된다.

- EC2 직접 설치
    - DB 보안 취약점 패치 → 개발자가 수동 진행
    - 데이터 백업 → 스크립트 직접 작성
    - 디스크 부족 → 직접 용량 늘리고 재부팅
    - DB 서버 뻗음 → 수동 복구
- AWS RDS 사용
    - DB 보안 패치 → 지정한 시간에 AWS가 자동 적용
    - 데이터 백업 → 클릭 한 번으로 자동 백업 & 스냅샷
    - 디스크 부족 → 디스크 스토리지 자동 스케일링
    - DB 서버 뻗음 → 멀티 AZ로 자동으로 예비 DB 스위칭

→ 백엔드 개발자가 DB패치나 백업에 시간을 빼앗기지 않고 오직 비즈니스 로직 개발에만 집중할 수 있게 만들어 주는 생산성 및 비용 절감 도구이다.

## RDS의 위치 & 엔드포인트 개념

RDS도 가상 서버(인스턴스)이므로, 리전 단위 자원이며 VPC 내부의 특정 가용 영역(AZ)프라이빗 서브넷에 안전하게 배치된다.

엔드포인트(DNS 이름 접속)

- RDS는 고정 IP를 주지 않고 고유의 DNS 엔드포인트 주소를 준다. → 장애가 발생해서 백업 DB인스턴스로 자동 교체되더라도, 스프링부트 애플리케이션의 application.yml에 적힌 DB 접속 주소(엔드포인트)를 고칠 필요가 없게 만들기 위해서이다.

## 고가용성 & 확장성

RDS에서 고가용성과 읽기 성능 향상을 위해서 어떤 구성을 썼는가?

| **구분** | **멀티 AZ (Multi-AZ) 배포** | **읽기 복제본 (Read Replica)** |
| --- | --- | --- |
| **목적** | **고가용성 (High Availability) & 장애 대비** | **성능 향상  & 읽기 부하 분산** |
| **구조** | 다른 가용 영역(AZ)에 **동기식 예비 DB (Standby)** 생성 | 다른 서버에 **비동기식 읽기 전용 DB** 생성 (1개 이상) |
| **작동 방식** | 평소에는 예비 DB로 쿼리를 보내지 않음. 메인 DB에 장애 발생 시 **AWS가 엔드포인트를 예비 DB로 자동 전환(Failover)** | 조회 쿼리가 너무 많을 때, **조회 트래픽만 읽기 복제본 DB로 나눠서 보냄** |
| **코드 반영** | 개발자가 코드나 엔드포인트를 고칠 필요가 없음 | **스프링 레벨에서 Write(CUD)와 Read(SELECT) 데이터소스를 분리**하도록 코드/설정 추가 필요 |

## 스프링 부트에서 RDS로 연결되는 실제 흐름

1. 스프링 부트 연결 준비
    
    application.yml에 RDS 엔드포인트 주소, DB이름, 포트를 세팅한다. (비밀번호는 하드코딩하지 않고 환경변수로 주입)
    
2. DNS 해석 및 RDS 도착
    
    앤드포인트 DNS 이름을 통해 VPC 내부 IP를 알아내고 RDS 인스턴스로 연결 요청을 보낸다.
    
3. RDS 보안 그룹 인바운드 통과
    
    RDS 문 앞을 지키는 보안 그룹이 요청을 검사한다.
    
    - 허용 포트 : MySQL3306
    - 허용 출발지 : 0.0.0.0/0이 아닌, “스프링 부트가 있는 EC2의 보안 그룹”만 지정해둬야 안전하다.
4. DB 인증 및 데이터 반환
    
    보안 그룹을 통과하면 RDS가 DB 계정/비밀번호를 최종 검증하고 쿼리 결과를 스프링 부트에 돌려준다.
    

## 정리

- RDS는 우리가 사용하던 RDB를 클라우드에서 생성하고 운영하고 확장할 수 있게 해주는 완전 관리형 서비스
- DB 자체는 동일하고 우리가 쿼리 작성하고 설계하고 인덱스 설정하는건 동일하고 설치하고 패치하고 백업하는 부문을 위임한다.
- 위치는 리전 안의 VPC 안에서 특정 가용 영역 서브넷 안에 있다.
- 접속할 때는 고정 IP가 아니라 엔드포인트라는 DNS 이름으로 접속을 한다. → 뒤에 인스턴스 바뀌어도 애플리케이션 입장에서는 설정 고치지 않아도 된다.
- 가용성이랑 확장을 도와주기도 한다. 멀티 AZ배포는 장애 났을 때 예비 인스턴스로 넘겨주는 일을 해줘서 중단 시간을 줄이고 리드 레플리카를 갖고 조회 부하를 나눠서 처리량 자체를 늘린다.
