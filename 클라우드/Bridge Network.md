## 설명할 수 있어야 하는 것

- 브릿지 네트워크가 무엇인가
- 한 Host 안에서 격리된 컨테이너들을 어떻게 하나로 묶어주는지
- 그 사이 오가는 요청이 어떤 경로를 따라서 이동하는지

## 정의

동일한 도커 호스트(EC2 1대) 내에서 독립적으로 격리된 컨테이너들을 하나의 사설 내부망으로 묶어 서로 통신할 수 있게 해주는 도커의 기본 가상 네트워크

왜 필요한가?

- 컨테이너는 기본적으로 격리되어있다
- 실제 웹 서비스는 Nginx(웹서버) → Spring Boot(API) → MySQL(DB)처럼 여러 컨테이너가 연동되어 동작해야한다.
- 브릿지 네트워크를 구축하면 DB포트를 외부에 퍼블릭으로 노출할 필요 없이, VPC 내부의 EC2 안에서 자기들끼리 안전하게 사설 IP/이름으로 쿼리를 주고받을 수 있다.

## 브릿지 네트워크의 내부 구성 요소

→ 컴퓨터 안에서 소프트웨어로 구현된 ‘가상 랜선’과 ‘가상 스위치’이다.

→ 앞에서 배운 AWS 네트워크랑은 계층이 다르다.

→ VPC는 EC2같은 AWS리소스가 놓이는 클라우드 상의 네트워크 경계 → 어떤 리소스가 어느 주소 대역에 속하고 어디까지 통신할 수 있을지 클라우드 차원에서 정리해주는 틀

→ 지금 배우는 브릿지 네트워크는 VPC 안에 위치한 EC2 한대. 도커 호스트 내부에서 컨테이너들을 연결하는 가상 네트워크

<img width="904" height="1096" alt="image" src="https://github.com/user-attachments/assets/e68ef5e2-bf14-4649-afb5-ac9cf5aee4d3" />


- docker0(Bridge) - 호스트 OS 상에 생성된 가상 L2 스위치 및 게이트웨이. 컨테이너 간 패킷을 중계함
- eth0(Container 내) - 컨테이너 입장에서 자기 자신에게 달려있는 가상 랜카드(출입구)
- veth pair(veth1, veth2) - 한쪽은 컨테이너 et0에, 반대쪽은 docker0 스위치에 꽂히는 가상 케이블(랜선)
- eth0(Host 컴퓨터) - EC2컴퓨터가 실제로 가진 진짜 물리 랜카드. 외부 인터넷 및 VPC 통신의 통로

#### 요청 이동 경로

**컨테이너 ↔ 컨테이너 통신(내부 통신)**

Spring Boot ↔ MySQL DB쿼리 전송

1. Spring Boot 컨테이너의 `eth0`에서 출발.
2. 가상 랜선(`veth1`)을 타고 가상 스위치(`docker0`)로 올라감.
3. `docker0`가 목적지인 MySQL의 가상 랜선(`veth2`)으로 패킷을 건네줌.
4. MySQL 컨테이너의 `eth0`에 도착! (**호스트 외부 인터넷으로 절대 나가지 않고 내부에서 안전 처리**)

**컨테이너 → 외부 인터넷 통신(아웃바운드)**

SpringBoot → 외부 결제 API 호출

1. Spring Boot 컨테이너의 `eth0` 출발 ➔ `veth1` ➔ `docker0` 스위치 도착.
2. 목적지가 외부이므로 `docker0`가 호스트의 진짜 물리 랜카드(`Host eth0`)로 패킷을 올림.
3. **NAT (Network Address Translation) 변환:** 컨테이너의 내부 사설 IP가 호스트 컴퓨터의 퍼블릭 IP로 변환되어 외부로 전송됨.

## 사용이유

컨테이너 간 통신을 격리된 네트워크 환경에서 안전하고 간편하게 관리하기 위해서

1. 컨테이너간 안전한 격리 통신

컨테이너들은 docker0라는 가상 스위치 내부에서만 서로의 주소로 대화한다

호스트 네워크나 외부 외부 인터넷에 노출되지 않는다. 통신은 하지만 범위를 격리된 내부망에 가둬둔다는 점이 이점

1. 서비스 간의 간편한 연결

웹서버 역할의 nginx컨테이너랑 DB역할의 MySQL컨테이너를 같은 브릿지 네트워크에 연결해두면 이름 기반 통신 덕분에 컨테이너 이름만으로 통신이 가능하다.

1. 포트 충돌 방지랑 노출 최소화

컨테이너들은 평소에는 내부 IP로 대화하다가 정말 바깥에 열어줘야하는 포트만 골라서 호스트 쪽에 연결한다. 

→ 포트를 호스트에 연결한다는 것은 외부 요청이 호스트의 특정 포트로 들어오면 그걸 컨테이너 포트로 이어준다는 뜻 

→ 필요한 것만 선택적으로 열어주어 안전

시큐리티 그룹이랑 구분하기

→ ec2같은 AWS 리소스 수준에서 움직이는 규칙

→ 브릿지 네트워크랑 포트 매핑하는 건 도커 호스트 내부의 경계고 통신을 구성할 때의 이야기

## 다른 네트워크 방식

#### Host NetWork

<img width="1060" height="536" alt="image" src="https://github.com/user-attachments/assets/3ee20e0d-679d-4d84-893e-c086f0026746" />


컨테이너가 호스트의 네트워크를 그대로 공유하는 방식

→ 별도의 가상 네트워크를 만들지 않고 호스트의 IP를 그대로 쓰는 방식

→ 브릿지는 컨테이너에게 별도의 가상 네트워크 인터페이스랑 사설 IP만들어서 격리했는데 호스트 네트워크는 그런 중간 계층 없이 호스트와 그냥 공유하는 방식이다.

→ 거쳐가는 단계가 없어서 네트워크 성능이 조금이나마 좋아질 수 있지만 그렇게 이득이 크지는 않다. 같은 IP써서 포트 겹치면 충돌이 나는 단점이 있다.

#### Overlay Network

<img width="1168" height="676" alt="image" src="https://github.com/user-attachments/assets/9e5ef9f9-3ad4-46d1-a35b-bc8020255ef8" />


앞에 배운 브릿지 네트워크는 호스트 한대 안의 이야기

→ 오버레이는 서로 다른 물리 호스트에 있는 컨테이너들을 같은 가상 서브넷으로 묶어서 마치 한 네트워크에 있는 것처럼 통신하게 만들어주는 역할

→ 호스트들이 패킷을 한번 감싸서 전달하는 방식으로 동작(캡슐화)

→ 이렇게 해서 다른 서버 위에 있는 컨테이너끼리도 같은 서브넷에 있는 것처럼 통신이 가능하다.

→ 한대 안에서 끝나는 브릿지랑은 다르게 여러 호스트를 걸쳐야할 때 쓰는 방식

#### Macvlan Network

<img width="1110" height="662" alt="image" src="https://github.com/user-attachments/assets/63277f35-39ed-435d-9083-c73393c97068" />


컨테이너에게 아예 별도의 Mac address랑 ip를 부여해서 컨테이너를 물리 네트워크의 일부처럼 동작시키는 방식

→ 맥 주소는 네트워크 장비마다 붙는 고유한 하드웨어 식별자

브릿지에서는 컨테이너가 docker0를 거쳐서 바깥과 통신했다.

→ 그런데 macvlan은 host의 네트워크 공간을 거치지 않고 컨테이너가 물리 스위치에 직접 노출된다.

→ 컨테이너가 네트워크 상의 독립된 장치처럼 보이게 된다.

→ 물리 네트워크랑 같은 레벨로 컨테이너를 붙이고 싶을 때 쓸 수 있는 방식

## 정리

- 브릿지 네트워크는 한대의 도커 호스트 안에서 서로 격리된 컨테이너들을 하나의 가상 내부망에 묶어서 통신하게 해주는 도커의 기본 네트워크
- 이런 구조에는 docker0라는 가상 스위치가 있고 veth pair(veth1,2)라는 가상 케이블이 각 컨테이너의 eth0랑 그 스위치에 연결한다.
- 요청이 가는 경로가 두 개다. 컨테이너 안에서 컨테이너끼리 통신하는 방식, 또 다른건 Host 거쳐서 NAT으로 Host IP로 외부랑 통신하는 방식
- 브릿지 네트워크를 쓰면 자동 내부 DNS 주소가 아니라 이름으로 접근해서 처리가 가능하다.
