## 정의와 착각하기 쉬운 포인트

사용자 관점에서 단 1초의 서비스 끊김(다운타임)이나 오류 없이 애플리케이션의 버전을 업데이트하는 배포 방식

서버 안에서는 구버전 프로세스가 꺼지고 신버전이 뜨는 변화가 일어나지만, 사용자 입장에서는 서비스가 계속 돌아가는 것처럼 느끼게 만드는 것

흔히 하는 착각 (무중단 배포와 고가용성은 같지 않다.)

- 무중단 배포 : 계획된 시스템 변경(배포)중 트래픽을 안전하게 전환하여 유저 다운타임을 없애는 기술
- 고가용성 : 서버 하드웨어 고장, 정전 등 예기치 못한 장애 상황에서도 서비스가 멈추지 않고 버티는 능력
- 무중단 배포를 위해 물리 서버 2대가 반드시 필요하지 않음. 단일 EC2 위에서 포트가 다른 도커 컨테이너 2개를 동시에 띄우는 공존 여유만 있어도 무중단 배포 자체는 가능하다. (단, 물리 서버 1대면 단일 장애점/SPOF 문제가 생기므로 실무에서는 고가용성을 위해 여러 서버를 둔다.)

## 무중단 배포가 성립하기 위한 조건

신버전 컨테이너 프로세스가 켜졌다고 바로 트래픽을 보내면 문제가 생긴다. 진짜 무중단 배포가 되려면 아래 조건이 갖춰져야 한다.

1. 헬스 체크 필수
    
    앱 프로세스가 떴다고 끝이 아니라, DB 커넥션 풀 연결, 초기화 등이 완료되어 실제 HTTP요청을 받을 준비가 되었는지 로드 밸런서가 확인한 후에 트래픽을 투입해야 한다.
    
2. 커넥션 트레이닝
    
    구버전 서버를 끌 때, 이미 처리 중이던 유저의 요청(작업)이 완료될 때까지 기다려준 뒤 프로세스를 종료해야 한다. (안 그러면 결제/이체 중이던 유저 요청이 차단된다.)
    
3. 데이터베이스 및 API 버전 호환성
    - v1과 v2가 동시에 켜져 있는 교체 구간이 반드시 존재한다.
    - 이때 DB 테이블 구조가 변경된다면, v1과 v2가 동시에 접근해도 터지지 않도록 데이터베이스 스키마 하위 호환성을 유지해야 한다.
4. 관찰 및 모니터링
    
    배포 후 실시간 에러율, 응답 지연 시간 지표를 관찰하여 신버전에 문제가 없는지 추적한다.
    
5. 즉각적인 롤백 대책
    
    신버전에서 심각한 오류가 감지되면 즉시 이전 구버전으로 트래픽을 돌릴 수 있는 비상 스위치가 준비되어 있어야 한다.
    

## 3가지 무중단 배포 전략

새 버전을 띄우는 교체 단위와 트래픽 전환 방식에 따라 3가지로 나뉜다.

#### 블루/그린 배포

구버전 환경(Blue)과 완벽히 동일한 크기의 신버전 환경(Green)을 통째로 하나 더 차려두고, Green의 헬스체크가 완료되면 로드 밸런서 스위치를 한 번에 Green으로 전환한다.

장점 : v1과 v2의 혼재가 없어 깔끔하다. 구버전이 그대로 살아있어 롤백 속도가 가장 빠르다.

단점 : 서버 자원을 2배로 띄워야 하므로 비용 부담이 가장 크다.

#### 롤링 배포

전체 10대의 서버 중 1~2대씩 순차적으로 트래픽을 빼고 v2로 교체한 뒤 다시 투입하는 과정을 굴려가며 반복한다.

장점 : 추가 서버 자원이 거의 들지 않아 가장 널리 쓰인다.(Kubernetes의 기본 배포 방식)

단점 : 배포 진행 중 구버전과 신버전이 동시에 유저 요청을 처리하는 버전 혼재 구간이 발생하며, 롤백에 시간이 걸린다.

#### 카나리 배포

전체 트래픽 중 아주 극소수(1% ~ 5%)만 신버전으로 흘려보낸 뒤, 지표를 모니터링하면서 이상이 없으면 비율을 10% → 50% → 100%로 확대한다.

장점 : 신버전에 치명적인 버그가 있어도 피해를 입는 유저 수가 극소수로 제한된다.

단점 : 트래픽 제어 및 모니터링 시스템 구축이 까다롭고 운영 복잡도가 높다.

## 정리

- 무중단 배포는 이미 배포 준비되어 있는 상태에서 다운타임 없이 사용자 입장에서 중단되지 않고 서비스 제공하는 배포이다.
- 무중단 배포 전략에서 봐야 하는 핵심은 다운타임이다. 기존 버전 먼저 내리고 새 버전을 올리면 빈 시간이 취급돼서 무중단 배포는 기존 버전 살려두고 새 버전 겹쳐두고 트래픽 옮겨서 사용자 관점에서는 문제 없이 돌아간다.
- 필요한게 꼭 물리서버 두대가 아니라 공존할 수 있는 실행 여유가 있으면 된다. 그런데 고가용성 때문에 실제 서비스에서는 당연히 여러 대의 물리 서버를 사용한다.
- 헬스체크로 준비 상태 확인하고 진행중인 요청 정리하고 버전간 호환성 생각하고 배포 이후 관찰이랑 롤백까지 같이 생각해야한다.
