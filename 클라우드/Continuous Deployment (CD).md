## 설명할 수 있어야 하는 것

- CD가 무엇이고 왜 필요한지
- CI랑 책임이 어디서 갈라지는지
- 왜 배포를 자동화하는지

앞서 배운 CI가 코드가 깨지지 않는지 자동으로 검증하는 단계였다면, CD는 검증을 마친 빌드 산출물(도커 이미지 등)을 실제 운영 환경까지 사람의 개입 없이 자동으로 전달하고 띄워주는 과정

## CD의 정의와 CI와의 책임 분리

<img width="942" height="370" alt="image" src="https://github.com/user-attachments/assets/8581282b-8be5-4a2d-8842-1c977db49ae9" />


코드가 자동화된 테스트(CI)를 통과하면, 사람이 직접 서버에 접속해서 명령어를 치지 않고 목표 환경(Staging, Production)까지 자동으로 전달 및 배포하는 프로세스

CI vs CD의 명확한 책임 경계:

- CI(검증) : 소스 코드를 대상으로 자주 통합, 자동 빌드, 자동 테스트를 수행하여 배포 가능한 상태인지 검증하는 역할
- CD(배포) : CI를 완벽히 통과한 결과물(도커 이미지, JAR 등)을 넘겨받아 실제 실행 환경으로 전달하고 실행하는 역할

[ 소스 코드 ] → [ CI: 자동 빌드 & 테스트 ] → [ CD: 이미지 생성 & 레지스트리 Push & EC2 배포 ]

## git push 한 번으로 완성되는 CI/CD 전체 파이프라인

개발자가 메인 브랜치에 코드를 머지하는 순간부터 운영 서버에 반영되기까지의 전체 흐름이다.

```
[ 개발자: git push / merge ]
       │
       ▼ (1. 이벤트 감지)
┌─────────────────────────────────────────────────────────────┐
│ 2. CI 단계 (GitHub Actions 러너)                               │
│    - 코드 가져오기 ➔ Gradle 빌드 ➔ 단위/통합 테스트 진행              │ 
│    - 테스트 실패 시 파이프라인 즉시 중단 (배포 X)                     │
└───────────────────────┬─────────────────────────────────────┘
                        │ (✔ 테스트 성공 통과)
                        ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. CD 단계 (GitHub Actions 러너 ➔ ECR ➔ EC2)                  │
│    - ① 검증된 코드로 [도커 이미지 빌드]                            │
│    - ② 완성된 이미지를 [ECR 레지스트리]에 Push                     │
│    - ③ 운영 서버(EC2)에 SSH 접속 또는 에이전트로 명령어 전달          │
│    - ④ EC2가 ECR에서 신규 이미지 Pull ➔ [컨테이너 재구동]           │
└───────────────────────┬─────────────────────────────────────┘
                        │
                        ▼
┌─────────────────────────────────────────────────────────────┐
│ 4. 배포 후 모니터링 & 리포트                                      │
│    - 헬스체크(Health Check) 수행 ➔ 슬랙(Slack)으로 성공 알림        │
└─────────────────────────────────────────────────────────────┘
```

1. CI 검증 완료
    
    러너 환경에서 자동 빌드 및 테스트가 통과되면, 검증된 소스 코드가 CD단계로 넘어간다.
    
2. 도커 이미지 빌드 & ECR Push
    
    러너가 Dockerfile을 읽어 컨테이너 이미지를 만든 후, 태그를 붙여 AWS ECR 레지스트리에 저장
    
3. EC2 서버 구동 명령
    
    배포 대상 서버가 ECR에서 방금 올린 신규 태그 이미지를 pull받아와 기존 컨테이너를 교체하여 구동한다.
    
4. 헬스체크 & 알림
    
    배포된 컨테이너가 정상 실행(Health Check)중인지 확인하고 슬랙으로 배포 완료 리포트 전송
    

## Continuous Delivery와 Continuous Deployment 차이

두 방식 모두 CD라고 부르지만, 최종 운영 환경 반영 전 사람의 승인이 필요한가?에서 차이가 갈린다.

- **Continuous Delivery(지속적 전달)**

CI 검증 → 빌드/이미지 생성 → 스테이징 환경 배포 → 사람 최종 승인 → 프로덕션 배포

- **Continuous Deployment(지속적 배포)**

CI 검증 → 빌드/이미지 생성 → 스테이징 환경 배포 → 자동 프로덕션 배포

| **구분** | **Continuous Delivery (지속적 전달)** | **Continuous Deployment (지속적 배포)** |
| --- | --- | --- |
| **운영 배포 방식** | **수동 승인**  | **100% 자동 배포** |
| **특징** | 배포 준비(이미지 빌드, 테스트)까지는 자동이지만, **운영 반영 스위치는 사람이 직접 누름** | 코드 Push부터 운영 반영까지 **인간의 개입이 전혀 없음** |
| **적용 사례** | **금융, 공공, 커머스 등** 보안 규제나 배포 일정(새벽 배포 등) 관리가 엄격한 시스템 | **스타트업, SaaS 서비스 등** 빠른 기능 릴리즈와 피드백이 중요한 시스템 |

## CD(배포 자동화)를 사용하는 이유

1. 휴먼 에러 제거
    
    사람이 직접 EC2에 접속해서 git pull, gradle build, docker run을 입력하다가 생기는 오타, 환경변수 누락, 수동 작업 실수를 걷어낸다.
    
2. 배포 지연 시간 절약
    
    배포에 소요되는 몇 시간의 단순 반복 작업을 몇 분 만에 완료하여, 개발자가 오직 코드 작성에만 집중할 수 있게 한다.
    
3. 작은 단위의 빠른 릴리즈
    
    배포에 대한 부담(비용)이 줄어들기 때문에, 하루에도 수차례 안전하게 기능을 배포하고 사용자의 피드백을 수용할 수 있다.
    

## 정리

- CD는 CI검증을 통과한 결과물을 목표 환경(개발, 스테이징, 프로덕션)까지 자동으로 전달하고 배포하는 과정이다.
- CI가 변경의 통합과 검증을 맡고 CD는 그 결과로 나온 빌드 산출물이나 컨테이너 이미지, 버전 정보를 받아서 실행환경에 올린다.
- CD 사용하는 이유는 사람이 손으로 하던 배포에서 생기는 지연이나 절차의 변동을 줄이고 반복 작업에서 오는 실수를 걷어내기 위해서 사용한다.
- CI/CD를 통해서 작은 변경을 자주내다보니 좋은 환경이 되고, 문제가 생겼을 때 원인이랑 영향범위를 좁히기 좋다.
