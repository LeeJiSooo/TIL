## 정의와 사용 이유

AWS 클라우드 내에서 사용자가 자신만의 논리적으로 격리된 네트워크 공간을 생성하고 관리할 수 있도록 하는 서비스

→ 물리적 격리가 아닌, AWS가 소프트웨어로 경계를 만들어주는 논리적 격리이다.

**존재 범위와 계층 구조:**

계정 > 리전 > VPC > 가용 영역(AZ)별 서브넷 > AWS 리소스(EC2)

VPC는 특정 리전 안에서 만들어지며(서울 리전 VPC는 도쿄에서 안 보임), 하나의 VPC는 리전내 여러 가용 영역(물리 데이터 센터)에 걸칠 수 있음

서브넷은 반드시 하나의 가용 영역 안에만 속함

**왜 애플리케이션 레벨이 아니라 ‘네트워크 레벨’에서 막아야 할까?**

- 애플리케이션 레벨 제어(ex.로그인 검사) : 공격자가 이미 서버 문 앞까지 도달한 뒤에 방어하는 것
- 네트워크 레벨 격리(VPC) : 아예 문 앞까지 접근조차 못 하게 길을 차단하는 것

데이터베이스(DB)를 프라이빗 서브넷에 두면, 외부 공격자가 DB비밀번호를 알고 있더라도 네트워크 연결 시작 자체가 불가능하므로 해킹과 데이터 유출을 원천 차단한다.

여러 프로젝트와 회사 계정이 물리 인프라를 공유하므로, 격리가 없으면 IP충돌, 의도치 않은 노출, 장에 전파 문제가 생긴다.

## VPC의 핵심 구성 요소(공간/경로/검사)

VPC의 구성 요소는 크게 공간을 나누는 것, 경로를 정하는 것, 검사하는 것으로 분류할 수 있다.

1. 공간을 나누는 구성 요소
- VPC : 내 네트워크의 전체 경계선을 긋는 것. 생성 시 사용할 IP 주소 범위(CIDR, 예: `10.0.0.0/16`)를 지정한다.
- 서브넷 : VPC의 IP 범위를 다시 쪼개어 만든 하위 네트워크 조각
    - 쪼개는 이유 : 용도별(보안 등급), 가용 영역별(장애 범위 분산)로 자원을 배치하기 위해서이다.  하나에 다 때려 넣으면 노출 수준을 구분할 수 없고, 특정 가용 영역 장애 시 대처가 안 된다.

1. 경로를 정하는 구성 요소(목적지를 적어둔 이정표와 문)
- 라우팅 테이블 : 목적지 IP 대역별로 패킷을 어디로 보낼지 적어둔 규칙 목록이다. 서브넷은 이 테이블을 하나씩 참조한다.
    - VPC 내부 대역으로 가는 규칙은 기본 내장되어 있어, 서브넷끼리는 별도 설정 없이 통신이 가능하다.
- 인터넷 게이트웨이(IGW) : VPC와 인터넷 사이에 놓인 양방향 문(VPC ↔ 외부 인터넷)
    - 라우팅 테이블에 모든 대역(`0.0.0.0/0`)을 인터넷 게이트웨이로 보내라는 규칙을 추가하면, 그 서브넷이 **퍼블릭 서브넷**이 된다.
- NAT 게이트웨이 : 프라이빗 서브넷의 자원이 외부로 나갈 수는 있지만, 밖에서 안으로 들어오는 것은 차단하는 일방통행 문이다.
    - 프라이빗 서브넷의 EC2가 외부 보안 패치를 받거나 외부 API를 호출해야 할 때 사용한다. IGW를 붙이면 들어오는 길도 열리기 때문에 비대칭 통제를 위해 필요하다.

1. 검사하는 구성 요소(방화벽 계층)

라우팅 테이블은 “길이 있냐 없냐”만 보지, 포트나 신원을 검사하지 않는다. 따라서 실제 통제는 이 계층이 담당한다.

- **네트워크 ACL (NACL):** **서브넷 전체**를 지키는 성벽 (상태 비저장형 / 허용, 거부 규칙 모두 다룸 / 들어올 때 열어줬어도 나갈 때 또 확인해야 함).
- **보안 그룹 (Security Group):** 서브넷 내부의 **개별 자원(인스턴스 등) 문 앞**을 지키는 수문장 (상태 저장형 / 허용 규칙만 다룸 / 들어오는 걸 허용하면 나가는 건 자동 허용).
    - *NACL이 필요한 이유:* 자원이 늘어날 때마다 보안 그룹을 붙이다 보면 실수가 생기므로, 구역 전체에 공통으로 걸리는 거부 규칙을 안전빵으로 만들어두기 위함.

## 트래픽이 통과하는 실제 순서(인바운드 / 아웃바운드)

퍼블릭 서브넷에 웹 서버(EC2)가 있고, 프라이빗 서브넷에 데이터베이스가 있는 구조

1단계 : 외부 사용자가 웹 서버(EC2)에 접속할 때

1. 사용자 요청이 인터넷을 거쳐 VPC 경계인 인터넷 게이트웨이(IGW)에 도착
2. 서브넷의 **라우팅 테이블**이 목적지를 확인하고 해당 퍼블릭 서브넷으로 안내
3. 퍼블릭 서브넷 경계에서 네트워크 ACL(NACL)이 인바운드 허용 여부 검사
4. 웹 서버 바로 앞에서 **보안 그룹**이 포트(예: 80, 443)와 출발지를 최종 검사
5. 모두 통과해야 인스턴스 안의 웹 서버 애플리케이션에 요청이 도달함

2단계 : 웹 서버가 내부 DB를 조회할 때

1. 웹 서버의 요청은 인터넷으로 나가지 않고, VPC 내부 경로(`local`)를 통해 프라이빗 서브넷으로 이동
2. 프라이빗 서브넷의 **NACL**과 DB 인스턴스의 **보안 그룹**이 "웹 서버로부터 오는 연결"을 허용하는지 검사 후 통과
3. 응답은 왔던 경로 그대로 다시 사용자에게 돌아감

“서비스 구축 시 퍼블릭 서브넷과 프라이빗 서브넷을 가르는 기준은 무엇이며, 어떤 자원을 배치하나요?”

- 판단 기준 : “이 자원이 외부 인터넷에서 직접적인 접근(요청)을 받아야 하는가?”
- 자원을 만들 때마다 판단하면 실수가 잦으므로, 서브넷 단에서 미리 성격을 정해두고 자원을 배치함으로써 기본 노출 수준을 통제한다.

| **서브넷 종류** | **핵심 기준** | **배치하는 주요 자원 (예시)** |
| --- | --- | --- |
| **퍼블릭 서브넷** | 외부 인터넷과 양방향 통신이 직접 필요한 자원 | 사용자 요청을 맨 앞단에서 받는 **로드 밸런서(ALB)**, 외부 노출용 웹 서버 등 |
| **프라이빗 서브넷** | 외부에서 직접 접근하면 안 되고, 내부 통신만 해야 하는 자원 | **비즈니스 로직 서버(API 서버/WAS)**, **데이터베이스(RDS)**, **캐시 서버(Redis)** 등 |

네트워크가 열려 있어도 권한이 없으면 작업이 거부되고, 권한이 있어도 네트워크가 막히면 연결이 안 된다. → 이들은 서로 다른 층에서 일하기 때문

- IAM : 이 사람이 이 자원을 생성/수정/삭제할 권한이 있는가? 판단(AWS API 작업 통제)
- VPC : 자원이 놓이는 네트워크 공간과 트래픽이 이동하는 대략적인 경로를 지정
- 보안 그룹 : 자원 바로 앞에서 어떤 포트와 출발지의 연결을 허용할지 결정
