## 정의

여러 대의 EC2 인스턴스(또는 컨테이너)로 들어오는 네트워크 트래픽을 자동으로 균등하게 분산해 주는 AWS의 관리형 로드 밸런서 서비스

- 단일 서버(EC2 1대)의 한계와 ELB의 필요성
    - 부하 한계 : 트래픽이 집중되면 1대의 CPU/RAM 범주를 초과해 서버가 다운된다.
    - 단일 한계점(SPOF - Single Point of Failure) : 서버 한대가 죽으면 서비스 전체가 멈춘다.
    - DNS 배분의 한계 : DNS(Route 53)에 IP를 여러 개 적어 둘 순 있지만, DNS는 서버의 ‘생사 여부’를 실시간으로 판별하여 장애 서버를 자동으로 제외하지 못 한다.
- ELB의 핵심 역할 :
    - 부하 분산(Load Balancing) : 요청 단위로 트래픽을 나눠 특정 서버만 바쁘고 나머지는 노는 상황을 방지한다.
    - 자동 장애 조치(Failover) : 죽은 서버를 실시간을 감지(Health Check)하여 정상적인 서버로만 트래픽을 전달한다.

## 트래픽 경로 & ELB의 위치

ELB는 특정 EC2에 붙는 게 아니라, VPC 내 복수의 가용 영역(AZ)서브넷에 진입점 노드를 두는 독립된 리소스이다.

```jsx
[사용자 브라우저]
      │ 1. 도메인(my-service.com) 입력
      ▼
  [Route 53] ──► ELB의 DNS 이름 (Alias 레코드) 반환
      │ 2. ELB 주소로 실제 HTTP/HTTPS 요청 전송
      ▼
  [  ELB  ] (리스너 80/443 수신 -> 대상 그룹 내 정상 EC2 선택)
      │ 3. VPC 내부 경로로 트래픽 전달
      ▼
 [보안 그룹] (ELB로부터 들어오는 인바운드 포트 허용 여부 검사)
      │ 4. 최종 전달
      ▼
  [EC2 / WAS] (실제 애플리케이션 로직 실행)
```

**ELB의 IP 특성**

ELB는 트래픽 양에 따라 AWS 내부적으로 노드를 늘리고 줄이기 때문에 고정 IP를 주지 않고 고유의 DNS 이름을 제공한다. 따라서 Route 53 연동 시 IP(A 레코드) 대신 AWS 리소스를 직접 가리키는 ‘별칭 레코드(Alias Record)’를 사용해야 한다.

## ELB의 구성 요소

1. 리스너
    
    ELB가 외부에서 어떤 프로토콜과 포트로 요청을 받을지 정하는 관문(예: `HTTP:80`, `HTTPS:443`)
    
2. 대상 그룹 :
    
    요청을 실제로 받아 처리할 백엔드 인스턴스들의 집합/목록
    
3. 헬스 체크 :
    
    ELB가 주기적으로 각 EC2에 핑/요청을 보내 정상적으로 응답할 수 있는지 물어보는 기능
    
    주체는 ELB : 서버가 스스로 “나 죽었어요”하는 게 아니라, ELB가 밖에서 계속 찔러보고 비정상 판단 시 해당 EC2를 트래픽 전달 대상에서 즉시 제외한다.
    

로드밸런서의 주요 유형(ALB vs NLB)

| **구분** | **Application Load Balancer (ALB)** | **Network Load Balancer (NLB)** |
| --- | --- | --- |
| **작동 계층** | **7계층 (애플리케이션 계층)** | **4계층 (전송 계층)** |
| **처리 프로토콜** | HTTP, HTTPS, gRPC, WebSocket | TCP, UDP, TLS |
| **트래픽 식별** | 요청의 내용(URL 경로, HTTP 헤더, 쿠키 등)을 직접 열어보고 해석함. | 패킷의 내용 파악 없이 IP/Port 수준의 연결(Stream)만 그대로 전달. |
| **주요 특징** | L7 라우팅 지원 (예: `/api` 경로 요청은 API 서버 그룹으로, `/web` 경로 요청은 Web 서버 그룹으로 찢어 보냄) | **극도로 빠른 속도 & 초저지연**. 수백만 개의 동시 연결(TCP) 처리 가능 |
| **추천 활용처** | **일반적인 웹 애플리케이션**, 마이크로서비스(MSA), REST API | 실시간 게임, 금융 거래, 대규모 소켓 통신, 고속 네트워크 환경 |

## 로드 밸런싱 알고리즘(트래픽을 나누는 기준)

**로드밸런싱을 할 때 어떤 알고리즘 방식으로 트래픽을 분산하는가?**

- 순차 배분(Round Robin)
    - 서버의 바쁜 정도와 상관없이 순서대로 1:1차례대로 배분한다.
    - 단점 : 요청마다 처리 시간이 극단적으로 다르면 특정 서버만 터질 수 있다.
- 최소 연결 방식
    - 현재 처리 중인 연결(요청) 수가 가장 적은 서버에게 우선 배분한다.
    - 장점 : 요청 처리 시간이 제각각인 웹 애플리케이션 환경에서 부하를 가장 효율적으로 균등배분한다.
- 가중치 방식
    - 서버의 사양이 서로 다를 때, 성능이 좋은 서버에 가중치를 두어 더 많은 요청을 보내도록 비율을 지정한다.
- 스티키세션(세션 고정)
    - 동일한 클라이언트의 요청은 계속 처음 접속했던 특정 EC2로만 지정하여 연결하는 방식
    - 단점 : 특정 서버에 부하가 쏠릴 수 있어 로드 밸런서 본연의 부하 분산 목적이 희석된다.

## Auto Scaling 연동 & 상태 관리(JWT/Redis)

ELB와 Auto Scaling(트래픽 변화에 따라 EC2수 자동 증감)이 만나면 확장성이 완성된다.

1. Auto Scaling이 새 EC2 생성
    
    트래픽이 급증하면 Auto Scaling Group이 새 EC2 인스턴스를 띄운다.
    
2. ELB 대상 그룹에 자동 등록
    
    새로 만들어진 EC2가 ELB의 대상 그룹 목록에 자동으로 등록되고, 헬스 체크 통과 후 바로 트래픽을 받아먹는다.
    
3. 트래픽 감소 시 대상 그룹에서 먼서 제외 후 종료
    
    트래픽이 줄어들면 ELB가 해당 EC2로의 새 요청 유입을 먼저 막고, 기존 처리 중인 요청이 끝나면 EC2를 종료시킨다.
    

**무상태 아키텍처의 중요성**

서버가 수시로 늘어나고 줄어들며 요청이 여러 EC2로 찢어지기 때문에, 로그인 세션 정보를 단일 EC2 인스턴스 메모리에 저장하면 안된다.(요청이 다른 EC2로 넘어가는 순간 강제 로그아웃된다.)

- 해결책1(JWT 토큰) : 로그인 상태 정보를 클라이언트(쿠키/헤더)가 갖고 다니도록 무상태 설계
- 해결책2(세션 클러스터링 - Redis) : 세션 정보를 특정 EC2가 아닌 중앙 캐시 서버(Redis)에 몰아 두고 모든 EC2가 동일한 Redis를 바라보게 처리한다.

## ELB를 활용한 보안 및 SSL 일괄 관리

- **SSL/TLS 오프로딩 (HTTPS 단일화):**
    - 443 HTTPS 리스너를 ELB에 붙여두면, **복잡한 암호화/복호화 연산을 ELB 한 곳에서 전담 처리한다.**
    - ELB와 백엔드 EC2 사이의 내부 통신은 안전한 VPC망이므로 HTTP(`8080`)로 가볍게 주고받을 수 있어 백엔드 서버 부하가 획기적으로 줄어든다.
- **AWS WAF (Web Application Server) 연동:**
    - ELB 바로 앞단에 웹 방화벽인 **WAF**를 붙여, SQL Injection이나 XSS 같은 악의적인 공격 패킷을 최전선에서 사전 차단한다.

## 정리

- ELB는 사용자 요청이 서버에 닿기 전에 먼저 통과하는 단일 진입점이다. → route 53이 알려준 주소가 ELB고 ELB가 요청을 받아 대상 그룹에서 대상을 고르고 보안 그룹 통과해서 EC2에 도달한다. 사용자는 EC2랑 직접 연결되지 않는다.
- ELB의 목적으로 여러대의 EC2 인스턴스가 있는 구성으로 서버를 돌릴 때 요청을 균일하게 나눠서 부하를 분산하기 위한 목적으로 사용한다.
- 구성요소는 크게 3가지이다. 리스너는 어떤 프로토콜과 포트로 요청 받을지를 결정하고 대상 그룹은 요청을 처리할 대상들을 묶고 헬스 체크는 그 중 지금 요청을 받을 수 있는 대상이 누구인지 판단하는 역할을 한다. ELB에서 헬스 체크 판단의 주체는 ELB가 된다.
