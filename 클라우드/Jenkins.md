## 설명할 수 있어야 하는 것

- 젠킨스가 전체 배포 흐름에서 어느 흐름에 있는 도구인지
- 깃헙 액션이랑 비교

## 정의와 깃허브 액션과의 차이

소프트웨어 개발 프로세스의 빌드, 테스트, 배포 작업을 자동화하는 자체 구축형 오픈소스 CI/CD도구

**깃허브 액션과의 가장 큰 차이점(운영 주체)** 

- 깃허브 액션 : 러너(Runner)가상 서버의 관리, 보안 패치, 인프라 운영을 GitHub이 모두 책임짐
- Jenkins : 젠킨스가 동작할 서버 구축, OS 관리, 접속 권한, 보안 패치까지 모두 팀/회사(운영자)가 직접 책임짐 → 자체 구축 방식

젠킨스 경험 유무 질문?

→ 젠킨스를 직접 다뤄본 적은 없지만, CI/CD 프로세스의 흐름과 젠킨스의 Controller-Agent구조는 이해하고 있다. 깃헙 액션을 통해 익힌 역량은 특정 도구의 사용법이 아니라 ‘자동화된 빌드/테스트/배포 파이프라인의 본질’에 있으므로, 젠킨스 환경에서도 빠르게 적응하여 배포 파이프라인을 다룰 수 있다.

## 핵심 용어 및 아키텍처

젠킨스는 파이프라인을 효율적으로 분산 처리하기 위해 컨트롤러와 에이전트 구조를 사용한다.

```
┌─────────────────────────────────────────────────────────────┐
│                 Jenkins Controller (지휘자)                   │
│  - Trigger 감지 (Git Push 이벤트, 정기 실행 등)                   │
│  - Job/Pipeline 흐름 제어 및 작업 분배                           │
└──────────────────────────────┬──────────────────────────────┘
                               │ (작업 배정)
                               ▼
┌─────────────────────────────────────────────────────────────┐
│                   Jenkins Agent (실제 일꾼)                   │
│  - Workspace: Git 코드를 받아와 임시 작업하는 디렉토리               │
│  - Build & Test: Gradle 컴파일 및 테스트 실행                    │
│  - Artifact 생성: JAR 또는 도커 이미지 결과물 생성                  │
└──────────────────────────────┬──────────────────────────────┘
                               │ (결과물 푸시)
                               ▼
                    [ AWS ECR 레지스트리 ]
                               │
                               ▼
                    [ 실제 운영 서버 EC2 ]
```

- Controller - 전체 젠킨스 시스템을 지휘하는 중심부이다. 작업 시각 및 이벤트를 감지(Trigger)하고, 어떤 작업(Job)을 어느 에이전트에 맡길지 결정한다. (과거에는 Master라고 부름)
- Agent - 컨트롤러의 지시를 받아 실제 빌드와 테스트 명령을 수행하는 작업 컴퓨터이다.(과거에는 Slave라고 부름. 깃헙 액션의 Runner와 동일 개념)
- Job/Pipeline - 젠킨스가 실행하는 하나의 자동화 작업 단위(Jenkinsfile이라는 코드로 전체 흐름을 정의)
- Workspace - 에이전트 내부에서 소스 코드를 내려받고 컴파일을 진행하는 임시 작업 디렉토리
- Artifact - 빌드 및 테스트 완료 후 나온 최종 배포 산출물(JAR파일 또는 도커 이미지)
- Plugin - Git 연동, 도커 작업, 슬랙 알림 등 필요한 기능을 자유롭게 확장할 수 있는 모듈 생태계

## 젠킨스 기반의 배포 파이프라인

<img width="2454" height="488" alt="image" src="https://github.com/user-attachments/assets/3192b48e-69ca-4c9f-bebe-df7d6f645998" />


1. Trigger(이벤트 감지) - 개발자가 Git에 코드를 push하면 Webhook 등을 통해 젠킨스 컨트롤러가 이를 감지한다.
2. Job 배정 및 Workspace마련(작업 배정) - 컨트롤러가 작업을 수행할 에이전트 노드를 지정하고, 에이전트 내부에 임시 Workspace를 생성한다.
3. Git Checkout(소스 수집) - 에이전트가 Git 저장소로부터 최신 소스 코드를 Workspace로 받아온다.
4. Build, Test & Artifact 생성(검증 및 포장) - Workspace 내부에서 테스트를 실행하고, 성공시 Dockerfile을 읽어 도커 이미지를 빌드한다.
5. Registry Push(보관) - 생성된 도커 이미지를 AWS ECR같은 중앙 레지스트리에 저장한다.(Workspace의 데이터는 휘발된다.)
6. Target Server Deploy(배포) - 운영 서버(EC2)로 커맨드를 전달하여, ECR에서 신규 이미지를 받아와 컨테이너를 구동한다.

## 기업에서 젠킨스를 사용하는 이유(장점)

1. 폐쇄망 및 사내 인프라(On-Premiss)보안
    
    금융, 공공, 대기업처럼 소스 코드가 외부 클라우드 서비스(GitHub)로 나갈 수 없고, 모든 빌드/배포가 사내 전용 내부망 안에서만 이루어져야 하는 조직에 필수적이다.
    
2. 압도적인 플러그인 생태계와 자유도
    
    오랜 역사를 가진 만큼 사내 레거시 시스템, 정적 코드 분석 도구, 복잡한 인프라 장비들과의 연동 플러그인이 매우 풍부하다.
    
3. 특수 커스텀 실행 환경 구성
    
    특정 OS, 고성능 하드웨어 GPU, 특수 빌드 도구가 세팅된 전용 에이전트 서버를 직접 구성하여 빌드 환경을 통제할 수 있다.
    

## 젠킨스 사용 시 수반되는 단점(운영 부담)

- 서버 관리 부담 : 젠키니스 서버가 죽으면 회사 전체의 배포가 마비되므로 가용성과 백업을 직접 챙겨야 한다.
- 플러그인 충돌 문제 : 플러그인 업그레이드 시 버전 호환성 문제가 자주 발생한다.
- 보안 패치 관리 : 젠킨스 자체의 보안 취약점 패치 및 자격 증명 관리를 내부 엔지니어가 지속적으로 수행해야 한다.

## 정리

- 젠킨스는 CI/CD프로세스를 구현하는 도구이다.
- git repo, 빌드랑 테스트 실행되는 환경, 이미지 위치하는 레지스트리, 배포대상 ec2까지 해서 4가지가 있고 이 사이에서 순서 조율시키는 자동화 서버이다.
- 트리거가 실행을 열고 컨트롤러가 잡을 맡을 에이전트를 정하고, 그 위에 워크페이스에서 빌드랑 테스트가 이뤄져서 이팩트가 만들어진다. 플러그인은 이 과정에서 필요한 기능들을 붙여준다.
- 깃헙액션이랑 가장 큰 차이는 실행환경에 대한 운영주체가 다르다. 젠킨스는 회사나 조직이 직접 관리하고 다뤄야 한다. → 상황에 따라서 맞게 쓰는게 필요하다.
