## 설명할 수 있어야 하는 것

- 빅뱅 배포가 무엇을 가리키는 말인지
- 왜 이렇게 했었는지
- 이 방식이 어떤 위험을 갖고 있는지

과거에는 왜 이 방식을 선택할 수밖에 없었는지(배경과 이유), 왜 지금은 도커와 CI/CD 기반의 소규모/자주 배포로 넘어가고 있는지 흐름을 중심적으로 이해하기

## 정의

여러 기능, 수정 사항, 리팩토링 등 수많은 변경점을 한꺼번에 모아두었다가 특정 시점에 운영 환경 전체를 통째로 교체하는 배포 방식

→ ‘빅뱅’이라는 용어는 도구나 기술의 이름이 아니라 “변경의 범위”와 “교체 방식”을 나타내는 키워드

→ 최신 도커 컨테이너 기술을 사용하더라도, 2달 치 커밋 100개가 담긴 이미지를 만들어서 기존 실행 중인 컨테이너를 끄고 한 번에 올려버린다면 그것도 빅뱅 배포에 해당한다.

```
[ 기존 버전 (v1.0) 운영 중 ]
             │
             ▼ (점검 시간 지정 ➔ 서비스 일시 중단!)
[ v1.0 컨테이너/서버 전체 다운 ]
             │
             ▼ (수십~수백 개 커밋이 포함된 v2.0 통째로 업로드)
[ 신규 버전 (v2.0) 일괄 전환 완료 ]
```

**장점**

1. 절차의 단순함 : 배포를 자주 하지 않으므로 관리자 승인, 점검 공지, 일시 점검 절차를 수십 개 변경점당 딱 1번만 진행하면 된다.
2. 초기 구축 비용 절약 : 자동화된 CI/CD 파이프라인이나 복잡한 무중단 배포 시스템을 구축하지 않아도 된다.

**단점 및 위험 요소**

1. 원인 파악의 불가능(디버깅 지옥) : 문제 발생 시 40개의 커밋 중 어떤 코드가 원인인지 스코프를 좁히기 매우 어렵다.
2. 동반 롤백의 피해 : 1개의 버그 때문에 정상 동작하는 나머지 39개의 기능까지 전부 이전 버전으로 롤백 해야 한다.
3. 다운타임 발생 : 두 버전이 트래픽을 나눠받지 못하고 구버전을 내리고 신버전을 올리는 순간 서비스가 일시 중단된다.

## 과거에는 왜 빅뱅 배포를 썼을까?

- 온프레미스(IDC 데이터센터)시대의 한계
    - 과거에는 서버 인프라를 증설하거나 변경하는 비용(실물 서버 구매, 랜선 연결, OS 설치)이 극도로 비쌌다.
    - 배포 한 번을 하려면 사람이 직접 데이터센터에 가거나 새벽 시간에 시스템을 끄고 밤샘 작업을 해야 했다.
    - 배포 행위 자체가 엄청난 돈과 인력(비용)이었기 때문에, 자주 배포하는 것이 불가능하여 수개월 치 코드를 쌓아 두었다가 한번에 털어 넣는 빅뱅 방시을 택할 수밖에 없었다.

## 현대 클라우드 & 도커 시대에서의 변화

현재 클라우드 & 도커(AWS/Docker)

→ 클릭 한 번으로 가상 서버/컨테이너 생성

→ 배포 = CI/CD 파이프라인으로 자동화 & 저비용

→ 소규모 단위 자주 배포

**왜 지금은 잘게 쪼개서 자주 배포할까?**

- AWS 같은 클라우드 환경 덕분에 서버나 컨테이너를 수시로 늘리고 줄이는 비용이 거의 없다.
- 도커로 실행 환경을 포장하고 CI/CD로 빌드/테스트를 자동화함으로써 배포 비용이 감소하였다.
- 커밋 1~2개 단위로 작게 자주 배포하면 :
    - 문제가 터져도 “방금 올린 1개 커밋이 원인이네”하고 바로 원인을 식별할 수 있다.
    - 롤백도 해당 커밋 1개만 되돌리면 되므로 운영 리스크가 낮아졌다.

## 정리

- 빅뱅 배포는 여러 변경사항을 큰 묶음으로 모아서 한 시점에 운영 환경에 적용하고 기존 버전을 통째로 교체하는 방식이다.
- 특정 서버 도구의 이름이 아니고 변경 범위랑 전환 방식을 가리키는 말이다.
- 컨테이너 이미지를 쓰더라도 전체를 한번에 갈아 끼운다면 빅뱅 배포이다.
- 장점은 단순화되어 편하다.
- 단점은 문제가 생겼을 때 원인을 좁히기 어렵고 롤백할 때 멀정히 돌아가는 기능까지 같이 롤백된다. + 서비스 중단 시간이 존재한다.
- 과거에는 클라우드 환경이 아니라 데이터센터같은 곳에서 호스팅 통해서 배포 진행해야했고 배포 자체에 들어가는 비용이 많다보니까 자주 배포하기 어려운 환경이 있었다.
