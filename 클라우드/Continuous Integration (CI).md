## 설명할 수 있어야 하는 것

- CI가 무엇이고 왜 필요한지
- 코드가 어떤 단계를 거쳐서 검증이 이루어지고 결과물이 되는지
- 검증이 실패하면 무엇이 어디서 멈추는지

## CI의 정의와 존재 이유

여러 개발자가 작성한 코드 변경 사항을 자주(주기적으로)중앙 저장소에 통합하고, 그 과정에서 자동 빌드 및 테스트를 거쳐 문제점을 조기에 발견하는 개발 프로세스

→ “큰 덩어리로 나중에 합치지 말고, 작게 쪼개서 자주 합치자”

**왜 필요한가?(빅뱅 통합의 지옥..)**

- 2명의 개발자가 2주일 동안 각자 코드를 짜고 나중에 한 번에 합치면, 충돌이 많이 발생하고 어디서 버그가 생겼는지 찾느라 힘들어진다.
- 매일, 혹은 기능 단위로 자주 PR을 올리고 코드를 합치면, 충돌이나 버그가 발생해도 방금 고친 몇 줄 안에서 바로 원인이 보인다.

## CI 검증 프로세스의 흐름

```
[ 1. 개발 (Local) ] ──► [ 2. 소스 관리 (GitHub) ] ──► [ 3. 자동 빌드 (Runner) ]
                                                          │
[ 5. 리포트 (Slack/PR) ] ◄── [ 4. 자동 테스트 (Test) ] ◄──────┘
```

1. 개발(Local Dev) : 개발자가 본인의 맥북/PC에서 기능 구현
2. 소스 관리 : 작성한 코드를 Git을 통해 중앙 저장소로 push
3. 자동 빌드
    
    개발자 개인 컴퓨터 환경이 아닌, CI도구가 준비한 독립되고 격리된 클린 환경(Runner/컨테이너)에서 코드를 받아와 컴파일 및 패키징 진행 
    
    → 공통의 약속된 표준 환경에서 안전하게 검증하기 위해서
    
4. 자동 테스트
    
    빌드된 결과물에 대해 단위테스트, 통합 테스트를 자동으로 돌린다.
    
    테스트가 하나라도 실패하면 다음 단계로 가지 않고 그 자리에서 즉시 빌드 중단한다.
    
5. 리포트
    
    검증 성공/실패 여부를 GitHub PR화면에 초록색 체크 또는 빨간색X 표시로 나타낸다.
    
    팀 슬랙 채널 등으로 담당자를 태그하여 결과를 실시간 알림
    

## git push 한 번으로 일어나는 실제 내부 과정

이 과정을 이해하면 도커가 CI 안에서 무슨 역할을 하는지 연결된다.

1. Push 이벤트 감지
    
    개발자가 git push를 실행하면, GitHub 저장소가 이 이벤트를 감지하여 미리 설정된 CI 워크플로우(YAML)를 트리거한다.
    
2. Runner(격리 환경)할당 & 도커 구동
    
    GitHub이 깨끗하게 비어있는 실행 환경(Runner)을 준비한다. 이때 도커 컨테이너 기술을 활용하여 항상 동일한 실행 환경을 복제한다.
    
3. Checkout & 의존성 설치
    
    러너 환경 내부로 방금 push된 코드를 가져와(checkout), JDK 등 언어 런타임과 라이브러리(build.gradle 등)를 다운로드한다.
    
4. Build & Test 수행
    
    `gradle bootJar`, `gradle test` 등을 실행함. 테스트가 깨지면 검증은 실패로 끝나고 빨간 `X`를 띄운다.
    

대표적인 CI 도구

| **구분** | **Jenkins (젠킨스)** | **GitHub Actions (깃허브 액션)** |
| --- | --- | --- |
| **특징** | 서버에 직접 설치해서 운영하는 **오픈소스 자체 구축형 도구** | GitHub 저장소 내부에서 바로 사용할 수 있는 **클라우드 서비스형(SaaS) 도구** |
| **장점** | 플러그인이 매우 풍부하며, 온프레미스/자체 폐쇄망 인프라 제어에 강력함 | 별도 서버 구축 없이 `.github/workflows/*.yml` 파일 하나로 즉시 사용 가능 |

## 실제 개발 팀의 협업 프로세스(PR과 CI)

1. 개발자가 본인 기능 브랜치에서 코딩 후에 PR을 생성
2. PR이 열리는 즉시 백그라운드에서 CI 파이프라인이 자동으로 가동
3. 동료 개발자가 코드 리뷰를 할 때 CI 검증 결과가 통과했는지 확인
4. 만약 CI 검증이 실패했다면 거절 → 비검증 코드가 메인 브랜치로 흘러 들어가는 것을 철저하게 방지

## 정리

- CI는 여러 개발자의 코드를 자주 통합하고 그때마다 자동으로 검증하는 프로세스
- 오랫동안 따로 작업하다가 한번에 합치면 충돌이랑 오류가 터져서 문제가 생기는데 자주 합치고 검증하면 문제가 작은 단위에서 해결된다.
- 흐름은 큰 틀에서 개발, 소스관리, 빌드, 테스트, 리포트의 과정으로 이루어진다.
- 코드가 내 로컬 환경에서 Repo로 가고 다시 CI 도구의 실행환경으로 옮겨가면서 프로세스가 이루어진다.
- CI의 범위는 운영환경에 배포되기 이전에 통합과 검증의 실패를 일찍 발견해서 검증되지 않은 코드가 운영으로 흘러가지 않게 막는다.
