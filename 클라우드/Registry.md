## 설명할 수 있어야 하는 것

- registry가 무엇인지, 왜 필요한지, 이미지가 어떤 방향으로 왔다 갔다 하는지
- registry가 배포의 일관성, 롤백에 어떻게 기여하는지

## 정의와 필요성

<img width="1110" height="684" alt="image" src="https://github.com/user-attachments/assets/dfe8c39e-1b49-4e21-8c08-9bf1f5dc221e" />


빌드된 컨테이너 이미지를 중앙에서 저장, 버전 관리, 분배하기 위해 제공되는 이미지 전용 중앙 저장소

**필요성(가장 큰 문제의 해결)**

- Dockerfile로 빌드한 이미지는 처음에는 개발자의 로컬 컴퓨터에만 존재한다.
- 실제 서비스가 구동되는 곳은 배포 대상 서버(EC2 인스턴스 등)
- 만든 곳(로컬)과 실행할 곳(서버)이 다른 문제를 해결하기 위해, 이미지를 중앙에 올려 보내고(push), 필요한 서버들이 다운로드(pull)받아 실행할 수 있게 해주는 중간 전달 창구가 레지스트리이다.

```
[ 개발자 로컬 PC ] ───── Push (이미지 올리기) ─────► [ Docker Registry ]
 (Dockerfile 빌드)                                     (이미지 중앙 보관)
                                                          │
 [ 운영 서버 EC2 #2 ] ◄──── Pull (이미지 받기) ────────────────┤
 [ 운영 서버 EC2 #1 ] ◄──── Pull (이미지 받기) ────────────────┘
```

- Docker Engine / Dockerfile : 실행 환경(이미지)을 빌드하고 관리하는 도구
- Docker Registry(Docker Hub, ECR) : 빌드된 이미지 결과물을 중앙에서 공유하고 주고받는 저장소

## 레지스트리의 핵심 동작 원리(레이어 재사용 & 버전 관리)

#### 레이어 단위 효율적 전송

- 이미지는 여러 개의 읽기 전용 레이어로 구성되어 있다.
- 레지스트리로 push하거나 pull할 때, 이미 저장소에 존재하는 레이어는 재전송하지 않고 변경되거나 추가된 레이어만 전송한다.
    
    → 덕분에 이미지 용량이 커도 실제 네트워크 통신량은 매우 적으며, 배포 및 전송 속도가 빨라진다.
    

#### 태그(Tag)를 통한 버전 관리 및 식별

동일한 이미지 이름에 콜론(:) 뒤에 태그(Tag)를 통해 버전 및 환경을 구별한다.

- `my-account/web-app:1.0` (1.0 버전 안정화 이미지)
- `my-account/web-app:1.1` (새로운 기능이 추가된 신규 버전 이미지)
- `my-account/web-app:latest` (가장 최근에 올린 이미지)

## 접근 권한 관리 & 자격 증명 주의사항

- Public & Private : 누구나 다운로드할 수 있는 공용 저장소와, 조직 내부 인원 및 허가된 서버만 접근 가능한 사설 저장소로 구분된다.
- 자격 증명 분리 원칙(보안 핵심)
    - Private 레지스트리에 접근하기 위한 인증 정보(비밀번호, 토큰 등)는 절대로 이미지 내부나 소스 코드파일에 하드코딩해서 포함시키면 안된다.
    - 이미지는 수평 확장시 수많은 서버로 유출될 수 있는 결과물이므로, 자격 증명은 EC2의 OS 환경변수나 AWS IAM Role 등을 통해 실행 환경에서 주입해야한다.

## Registry를 사용하는 이유

#### 배포의 일관성

모든 개발자와 운영서버, CI/CD 파이프라인이 동일한 중앙 레지스트리에서 검증된 단 하나의 이미지 사본을 내려받아 실행하므로, 환경에 따른 동작 차이가 완벽히 사라진다.

#### 배포 자동화(CI/CD Pipeline)

개발자가 코드를 Push하면, CI/CD 도구(GitHub Actions, Jenkins 등)가 자동으로 이미지를 빌드하여 레지스트리에 push하고, 서버가 이를 pull받아 재생성하도록 파이프라인을 자동화할 수 있음

#### 롤백하기 쉬움

- 문제 발생 상황 : 신규 버전(web-app:1.1)을 배포했는데 심각한 버그가 발생한 경우
- 레지스트리가 없을 때 : 코드원복 → 다시 빌드 → 서버로 수동 전송하는 등 긴 시간이 소요됨
- 레지스트리가 있을 때 : 레지스트리에는 이전 안정 버전(web-app:1.0)이 그대로 보존되어 있다. 배포 서버에서 단지 태그를 1.0으로 재지정하여 pull받은 뒤 컨테이너를 다시 띄우면 다시 정상 원복된다.

주요 레지스트리 제품

- Docker Hub : 도커 공식 기본 레지스트리(공용 이미지 다수 보유)
- AWS ECR(Elastic Container Registry) : AWS에서 제공하는 완전관리형 사설 레지스트리(IAM 권한 연동 및 VPC 내부 보안에 강력)
- Google Artifact Registry / Github Container Registry : 각 클라우드 및 플랫폼 연동형 레지스트리

## 정리

- 레지스트리는 컨테이너 이미지를 중앙에 저장하고 나눠쓰는 저장소
- 도커파일로 재현 가능한 이미지를 만드는데까지 왔다면 레지스트리는 그 이미지를 만든 곳에서 실행한 곳으로 옮기는 역할
- 깃헙이랑 비슷하게 개발환경에서 만든 이미지 저장소로 올리는 push, 배포 대상 서버가 저장소에서 내려받는 pull
- 레지스트리를 쓰는 이뉴는 일관성, 자동화, 롤백 편의성 때문이다.
