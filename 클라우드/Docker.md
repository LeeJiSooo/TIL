## 설명할 수 있어야 하는 것

- 도커가 무엇이고 어떤 문제를 푸는지
- 도커를 이루는 구성요소들이 어떤 책임을 맡고 있는지
- 예전부터 쓰던 가상 머신과 구조가 어떻게 다른지

## 도커가 해결하려고 한 진짜 문제

- 문제 상황 : 내 맥북(Java 17)에서는 완벽하게 돌아가는데, 배포할 EC2(Java 11)에 올리니까 에러가 난다.
    - OS, 언어 런타임, 라이브러리 버전, 설정값 등 실행 환경이 달라서 발생하는 문제
    - 서버가 10대, 20대로 늘어나면 일일이 접속해서 환경을 똑같이 맞춰주는 작업은 힘들다.
- 도커의 해결책 : 애플리케이션 코드뿐만 아니라, 그 코드가 도는 데 필요한 런타임, 라이브러리, 설정까지 전부 한 덩어리로 포장(Container)해 버린다.
- 결과 : 내 노트북에서 포장한 상자 그대로 서버에서 실행하기 때문에, 어디서 실행하든 동일한 실행 환경이 재현된다.

## 도커 구성요소

- 도커파일 : 이미지를 어떻게 만들지 단계별로 적어둔 설계도(텍스트 문서)
- 이미지 : 코드, 라이브러리, 설정이 담긴 실행 전의 불변 결과물(한 번 만들어지면 안 변함)
- 컨테이너 : 이미지를 실행해서 메모리 위에서 돌아가고 있는 살아있는 프로세스(격리된 실행 공간)
- 레지스트리 : 만들어진 이미지를 보관하고 나눠주는 중앙 저장소(ex. 도커 허브)
- 도커 데몬 : 백그라운드에서 돌면서 도커파일을 읽어 이미지를 빌드하고, 컨테이너를 띄우는 실제 일꾼

컨테이너의 휘발성 : 컨테이너는 언제든 지우고 새로 띄우는 소모품 개념이다. 컨테이너를 지우면 내부에 쌓인 데이터(쓰기 계층)도 날아가기 때문에, DB데이터 같은 영구적인 자료는 절대 컨테이너 내부에 저장하면 안 되고 RDS나 S3, 도커 볼륨을 써야 한다.

## 도커 빌드 및 실행 순서

<img width="1368" height="554" alt="image" src="https://github.com/user-attachments/assets/9007eeb5-bbb1-4d03-9213-55b83cb1be7b" />


애플리케이션이 도커를 통해 서버에 올라가는 과정

1. Dockerfile작성
    
    개발자가 프로젝트 폴더 안에 애플리케이션 실행 환경을 정의한 Dockerfile을 작성한다.
    
2. Image Build(빌드)
    
    도커 데몬이 Dockerfile을 읽고, 필요한 재료를 모아 불변의 결과물인 도커 이미지를 만들어낸다.
    
3. Registry Push(업로드)
    
    만들어진 이미지를 다른 서버에서도 받을 수 있도록 도커 허브같은 레지스트리에 올려둔다.
    
4. Pull & Run(다운로드 및 실행)
    
    운영 서버의 도커 데몬이 레지스트리에 이미지를 내려받아 컨테이너로 실행하여 사용자 요청을 처리한다.
    

## 가상머신과 도커(컨테이너)비교

<img width="1202" height="512" alt="image" src="https://github.com/user-attachments/assets/310acc6a-3540-407e-a02a-4d2cc3bc15ce" />


도커가 왜 ‘가볍다’고 하는지 이해하려면, 예전부터 쓰던 가상 머신(VM)과 비교해서 봐야 한다.

- 공통점 : 물리 서버 한 대의 자원을 쪼개서, 여러 애플리케이션을 격리하여 실행하게 해준다.(비싼 서버 자원 낭비 방지)
- 차이점 : ‘OS와 커널’을 어떻게 다루는가

| **구분** | **가상 머신 (VM / VPS)** | **도커 (Container)** |
| --- | --- | --- |
| **비유** | **단독 주택 여러 채 짓기** (집마다 보일러, 배관 다 따로 설치) | **큰 건물 안의 원룸들** (중앙 보일러 하나를 건물 전체가 공유) |
| **구조** | 물리 서버 ➔ 하이퍼바이저 ➔ **게스트 OS (통째로 설치)** ➔ 앱 | 물리 서버 ➔ 호스트 OS ➔ 도커 엔진 ➔ 앱 |
| **커널(Kernel) 공유** | VM마다 무거운 게스트 OS와 커널을 따로 가짐 | **호스트 OS의 커널을 모든 컨테이너가 공유함** |
| **무게와 속도** | 기가바이트 단위로 무겁고, 부팅 시간 오래 걸림 | 런타임/라이브러리만 담아 메가바이트 단위로 가볍고, **실행(부팅) 속도가 초 단위로 빠름** |
| **격리 수준 (보안)** | 완벽하게 분리되어 있어 **격리성이 강함** | 커널을 공유하므로 VM에 비해 격리 수준은 낮음 (호스트 커널이 뚫리면 다 같이 위험해질 수 있음) |

그럼 무조건 도커가 좋냐? 

→ 아니다.

→ 빠르고 일관된 배포가 필요 할 때는 도커가 유리하지만, 호스트와 완벽하게 분리된 강력한 보안 격리가 피요한 시스템(금융 코아망 등)에서는 여전히 VM(가상 머신)을 선택하는 것이 좋다.
