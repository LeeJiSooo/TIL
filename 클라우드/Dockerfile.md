## 도커파일의 정의와 필요성

도커 이미지를 생성하기 위한 명령어와 설정이 순서대로 적힌 텍스트 기반의 설계도

왜 환경을 ‘코드’로 적어두는가?

- 기억 기반 설치의 한계 : 누군가 서버나 컨테이너에 직접 들어가 손으로 설치하면, 시간이 흐른 뒤 무슨 버전을 어떤 순서로 했는지 재현이 불가능하다.

도커파일의 이점 :

- 재현성 & 협업 : 파일 하나만 공유하면 전 세계 누구나 동일한 실행 환경을 새로 빌드할 수 있다.
- 자동화 : CI/CD 파이프라인에서 수동 작업 없이 명령어 하나로 이미지 빌드 자동화
- 유지보수 : 환경 변경 시 서버에 들어갈 필요 없이 도커파일을 수정해 깃으로 버전 관리를 한다.

## 도커파일 지시어 분석(스프링 부트 예시)

도커파일 내부의 지시어는 실행 시점에 따라 이미지 빌드 시점과 컨테이너 실행 시점으로 구분된다.

```docker
# 1. FROM: 빌드의 출발점이 되는 베이스 이미지 (JDK + Gradle 환경)
FROM gradle:8-jdk17

# 2. WORKDIR: 이후 명령들이 실행될 이미지 내부의 기본 작업 디렉터리 설정
WORKDIR /app

# 3. COPY (의존성 파일만 먼저): 자주 안 바뀌는 설정 파일을 먼저 복사 (캐싱 극대화)
COPY build.gradle settings.gradle ./

# 4. RUN: [빌드 시점] 의존성 라이브러리를 먼저 다운로드 (독립 레이어로 저장)
RUN gradle dependencies --no-daemon

# 5. COPY (소스 코드 전체): 자주 바뀌는 자바 코드는 뒤쪽에 배치
COPY . .

# 6. RUN: [빌드 시점] 자바 코드를 컴파일하여 실행 가능한 JAR 파일 생성
RUN gradle bootJar --no-daemon

# 7. EXPOSE: 문 문서화 및 의도 선언 (실제 포트를 열어주는 것은 아님!)
EXPOSE 8080

# 8. CMD: [컨테이너 실행 시점] 이미지 빌드가 끝난 후, 컨테이너가 뜰 때 실행될 최종 명령어
CMD ["java", "-jar", "build/libs/app-0.0.1-SNAPSHOT.jar"]
```

| **구분** | **해당 지시어** | **실행되는 시점** | **설명** |
| --- | --- | --- | --- |
| **빌드 시점** | `FROM`, `WORKDIR`, `COPY`, `RUN` | **`docker build` 실행 중** | 도커 데몬이 한 줄씩 실행하며 결과물을 **읽기 전용 레이어**로 만듦. |
| **실행 시점** | `CMD`, `ENTRYPOINT` | **`docker run` 실행 직후** | 이미지는 완성된 상태이며, **컨테이너 프로세스가 켜질 때** 1번 실행됨. |

## 레이어 캐싱과 성능 최적화 전략

도커파일의 한 줄은 하나의 독립된 읽기 전용 레이어가 된다. 도커는 빌드 속도를 높이기 위해 이전 빌드 결과를 캐싱해서 재사용한다.

1. 의존성 라이브러리 다운로드
    
    build.gradle을 먼저 복사하고 gradle dependencies를 실행한다. 라이브러리가 변경되지 않는 한 이 레이어는 캐시되어 다시 다운로드하지 않고 빠르게 통과한다.
    
2. 자바 소스 코드 복사 및 빌드
    
    소스 코드는 개발 중 매번 수정된다. 이 지점부터 캐시가 깨지며, 아래쪽의 gradle bootJar만 실제로 새로 빌드한다.
    

→ 자주 안 바뀌는 것(의존성, OS 설정)은 위쪽에, 자주 바뀌는 것(소스 코드)은 아래쪽에 배치한다.

→ 만약 소스 코드 복사를 맨 위에 두면, 코드 한 줄 고칠때마다 아래의 라이브러리 다운로드까지 전부 처음부터 다시 수행하여 CI/CD빌드 시간이 길어진다.

## OverlayFS(통합 파일 시스템)동작 원리

도커가 “여러 개의 읽기 전용 이미지 레이어”와 “1개의 쓰기 전용 컨테이너 레이어”를 어떻게 하나로 합쳐서 보여주는지의 내부 원리이다.

<img width="1196" height="670" alt="image" src="https://github.com/user-attachments/assets/95c57f8e-7595-43b9-aeb9-0bfc1b2de172" />


1. LowerDir(이미지 레이어들) : 도커파일 명령어들이 만든 읽기 전용 디렉토리들의 집합 → 절대 수정되지 않음
2. UpperDir(컨테이너 레이어) : 컨테이너가 켜질 때 새로 생성되는 유일한 쓰기 기능 디렉토리
3. MergedDir(통합 디렉토리) : LowerDir들과 UpperDir를 하나로 겹쳐서 컨테이너 안의 프로세스에게 보여주는 최종 파일 시스템
4. 읽기/수정 동작 방식(CoW):
    - 읽기 : UpperDir부터 찾고, 없으면 LowerDir를 아래로 내려가며 검색
    - 수정 : LowerDir의 원본을 고치지 않고, 수정할 파일을 UpperDir로 복사해온 뒤 복사본을 수정

## 정리

- 도커파일은 이미지 만들기 위한 명령어랑 설정을 담은 텍스트 설계도, 지시서이다.
- 이미지랑 컨테이너의 출발점
- 도커파일 안에서 빌드 시점과 실행 시점의 명령어들이 섞여있다.
    - FROM, COPY, RUN은 이미지 빌드하는 동안 실행되고
    - CMD, ENTRYPOINT는 그 이미지로 컨테이너를 띄운 직후에 실행된다.
- 도커파일 쓰는 이유는 환경을 사람의 기억이 아니라 코드로 관리하기 위해서 쓴다. → 재현성, 자동화, 유지보수, 협업
- 각 명령이 레이어로 쌓이고 캐싱되기 때문에 자주 안바뀌는 건 위에, 자주 바뀌는 건 아래에 두는 배치가 빌드 성능 영향을 미친다.
