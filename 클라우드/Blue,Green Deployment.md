## 설명할 수 있어야 하는 것

- 블루랑 그린이 각각 어떤 역할을 하는가
- 문제가 생겼을때 롤백을 어떻게 하는가

## 정의

독립적으로 트래픽을 처리할 수 있는 두 개의 환경(Blue, Green)을 나란히 운영하며, 라우터(로드밸런서 등)의 트래픽 목적지를 한순간에 전환하여 다운타임 없이 배포 및 롤백을 수행하는 무중단 배포 방식이다.

핵심 속성

- 블루 : 현재 실제 유저의 요청을 받아내고 있는 ‘안정적인 운영 환경’
- 그린 : 새 버전을 미리 배포해 두고 트래픽 전환을 기다리는 ‘후보 환경’

→ 색상 명칭은 관례일 뿐 고정된 역할이 아니다. 트래픽을 Green으로 전환하는 순간, 이제 Green이 운영 환(Blue 역할)이 되고 기존의 Blue는 대기 환경이 되는 상대적인 개념이다.

```
[ 초기 상태 ]
 사용자 트래픽 ──► [ 라우터 (ALB / Nginx) ]
                          │
                          ├────────► [ Blue 환경 (v1.0 - 운영 중) ]
                          └─(차단)──► [ Green 환경 (v2.0 - 대기 중) ]

─────────────────────────────────────────────────────────────

 [ 트래픽 스위치 전환 후 ]
 사용자 트래픽 ──► [ 라우터 (ALB / Nginx) ]
                          │
                          ├─(차단)──► [ Blue 환경 (v1.0 - 대기/정리) ]
                          └────────► [ Green 환경 (v2.0 - 운영 전환 완료) ]
```

환경이 다르면 그린에서의 테스트 결과를 신뢰할 수 없으므로 동일한 스펙 유지가 필수적이다.

## 한계점과 비용 및 데이터 이슈

블루/그린 배포는 단순하고 명확하지만, 실제 운영 환경에서는 아래 두 가지 현실적인 문제를 고려해야한다.

#### 자원 고정 비용

- 배포 시점 동안 인프라 환경을 2배로 띄워야 하므로 비즈니스 비용(서버 대야료)이 크게 증가한다.
- 운영/개발자 관점에서의 어필  - 성능 개선 / API 최적화를 진행할 때 수치적 TPS상승에만 그치지 않고, “단일 인스턴스의 스펙을 낮춰서 인프라 고정 비용을 감축시켰다”는 관점으로 어필하면 실무 운영 측면에서 강력한 강점이 된다.

#### 공유 데이터베이스 스키마 변경 시 롤백의 한계

- 일반적으로 인스턴스는 2벌(Blue/Green)을 띄우지만, DB는 데이터 일관성을 위해 단 1개를 공유한다.
- 문제 상황 : 그린 환경 배포 시 DB컬럼명을 바꾸거나 삭제하면, 아직 트래픽을 처리 중인 블루 환경의 DB조회가 즉시 실패되며 롤백도 불가능해진다.

**해결책 : 단계별 DB 스키마 분리 전략(Expand-Contract Pattern)**

컬럼 변경을 한 번의 배포에 몰아넣지 않고, 트래픽 전환 시점과 DB 스키마 변경 시점을 분리해야 한다.

[1단계 : 컬럼 추가(Expand)]

-기존 컬럼을 지우지 않고, 신규 컬럼을 DB에 추가한다.

-구버전(Blue)은 기존 컬럼을 쓰고, 신버전은 신규 컬럼을 쓰도록 작성하여 호환성을 유지한다.

[2단계 : 블루/그린 배포 진행]

트래픽을 Green으로 안전하게 전환 → 양쪽 버전 모두 DB 오류 없이 구동 가능하다.

[3단계 : 데이터 이관 및 기존 컬럼 삭제]

배포가 완벽히 안착하면 기존 컬럼 데이터를 신규컬럼으로 마이그레이션한 뒤, 기존 컬럼을 삭제한다.

## 정리

- 블루/그린 배포는 독립된 2개의 환경을 나란히 띄우고, 라우터 스위칭을 통해 한순간에 트래픽을 전환하는 무중단 배포 방식이다.
- 개념이 단순하고, 문제 발생 시 스위치만 되돌리면 되므로 롤백 속도가 극도로 빠르다.
- 주의점
    - 배포 동안 인프라 자원이 2배로 들므로 서버 비용 발생
    - 공유 DB의 스키마를 변경할 때는 이전 버전과의 하위 호환성(컬럼 동시 존재)을 보장하는 단계적 배포 전략이 필수적이다.
