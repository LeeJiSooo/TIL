## 정의와 주요 특징

동적으로 IP가 변경되는 클라우드 환경에서도 외부 주소를 고정하기 위해 사용되는 AWS 계정 기반의 정적(고정)퍼블릭 IP 주소

- 주소 소유 주체(계정 vs 인스턴스)
    - 일반 퍼블릭 IP는 EC2인스턴스에 종속되어 있어 인스턴스를 중지후 재시작하면 주소가 바뀌어 버린다.
    - Elastic IP는 인스턴스가 아니라 ‘AWS 계정’에 할당되는 자원이다. 명시적으로 반납하기 전까지 내 계정에 유지된다.
- 핵심 상태 분리(할당 vs 연결)
    - 할당 : 이 IP 내 계정 소유로 찜한다.(계정에 IP 확보)
    - 연결 : 이 IP로 들어오는 트래픽을 특정 EC2 인스턴스로 보내준다.(대상 지정)
    - 분리 : 인스턴스를 버려도 IP는 내 계정에 그대로 남아 있다.
- 리전 범위 : 리전 단위 자원(서울 리전에서 할당받은 Elastic IP는 서울 리전 내 인스턴스에만 붙일 수 있다.)

## 왜 고정 IP가 필요한가?

운영환경에서 EC2를 껐다 켰을 때 퍼블릭 IP가 매번 달라지면 다음과 같은 문제가 벌어진다.

- DNS(도메인)설정 불일치:
    - 사용자는 https://my-service.com로 들어온다. DNS는 도메인 이름을 IP주소로 변환해준다.
    - IP가 바뀌면 DNS가 이미 사라진 옛날 주소를 가리키게 되어 서비스 접속이 끊긴다.
- 외부 서비스의 허용 목록 이탈
    - 결제 대행사(PG)나 외부 보안 API는 보안을 위해 “등록된 특정한 IP에서 오는 요청만 수락”한다.
    - 서버 IP가 바뀌면 외부 api호출이 전부 거부된다.
- 보안/CORS 설정 번거로움
    - 스프링 시큐리티, CORS 허용 범위, 보안 그룹 인바운드 규칙 등 IP 기반으로 설정된 모든 규칙을 매번 손수 바꿔야 한다.

“인스턴스 교체 시의 유연함”

상황 : 기존 EC2 서버에 에러가 생겨 버리고, 도커 이미지를 이용해 완전히 새로운 EC2인스턴스를 띄운다.

작업

1. Elastic IP를 기존 장애 인스턴스에서 ‘분리’한다.
2. 새로 띄운 EC2 인스턴스에 Elastic IP를 ‘연결’한다.

결과 : 외부 사용자가 바라보는 서비스 주소(IP/도미엔)는 단 하나도 바뀌지 않았다.

→ DNS 레코드를 새로 고치거나 PG사에 연락해서 IP 변경 신청을 할 필요가 없다. (작업의 영향 범위가 줄어든다.)

## 주소 고정 vs 네트워크/보안 차이점(위치 분석)

요청이 외부에서 우리 서비스로 들어올 때, 각 요소가 관여하는 지점과 책임이 완전히 다르다.

```json
[인터넷 사용자]
      │
      ▼
 1. Elastic IP (주소 판별) : "트래픽이 어디 주소로 찾아왔는가?" (VPC 입구)
      │
      ▼
 2. 보안 그룹 (포트/소스 검사) : "이 주소로 온 트래픽의 포트/출발지를 허용할 것인가?"
      │
      ▼
 3. IAM (권한 평가) : "누가 Elastic IP를 할당/연결하는 AWS API 작업을 수행할 수 있는가?"
```

Elastic IP를 붙였다고 해서 접속이 바로 되는 것이 아니다!

→ Elastic IP는 단지 집 주소를 고정해 준 것일 뿐, 그 집 문(보안 그룹 포트)이 닫혀 있거나 길(VPC 라우팅)이 막혀 있다면 접속되지 않는다.

## 정리

- Elastic IP는 AWS 계정에 할당되는 리전 단위 고정 퍼블릭 IP 주소
- 인스턴스에 속하는 게 아니라 계정이 보유하는 자원
- 할당이랑 연결이 분리되어 있다. 그래서 인스턴스 중지하거나 아예 교체해도 바깥에서 보는 주소는 그대로 유지가 가능하다.
- Elastic IP를 쓰는 이유는 퍼블릭 IP가 인스턴스 중지했다가 재실행하면 재할당되어서 계속 바뀌기 때문에 유지가 필요해서이다. 유지 하지 않으면 여러 문제가 발생한다.
