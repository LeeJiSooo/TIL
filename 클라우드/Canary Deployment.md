## 설명할 수 있어야 하는 것

- 카나리 배포가 무엇이고 어떤 과정으로 이루어지는지
- 구버전이랑 신버전 사이에서 트래픽이 어떤 순서로 이동하는지

## 정의 및 존재 이유

새 버전을 전체에 적용하기 전에, 실제 운영 트래픽 중 극소수의 비율/대상에게만 먼저 노출하여 실환경 반응 및 지표를 검증한 후 점진적으로 전면 배포하는 무중단 배포 전략

개발 / 스테이징 환경의 가짜 테스트에서는 나타나지 않던 실제 운영 환경(복잡한 기기, 실제 유저 데이터)의 예측 불가능한 장애 위험을 극소수로 제한하기 위함이다.

## 롤링 배포와의 차이점

두 방식 모두 구버전과 신버전이 동시에 존재하며 점진적으로 넘어가지만, 공존을 바라보는 ‘목적’이 다르다.

- 롤링 배포 → 교체 완료를 향해 지속적으로 ‘순차적 굴러가는 진행’
- 카나리 배포 → 안전한지 판단하기 위한 ‘의도적인 한정 노출 & 관찰’

| **구분** | **롤링 배포 (Rolling)** | **카나리 배포 (Canary)** |
| --- | --- | --- |
| **공존의 목적** | 모든 인스턴스를 새 버전으로 교체해 나가는 **과정** | 안전성을 모니터링하기 위한 **의도적인 제한 노출** |
| **시간 흐름** | 1대씩 빠르게 교체하며 연속 진행 | 1% 배포 후 **수 시간~며칠 동안 멈춰서 관찰**함 |
| **제어 대상** | 인스턴스 개수/단위 교체 | **트래픽 비율(%) 또는 특정 유저 그룹** 제어 |


## 트래픽을 라우팅하는 방식과 타겟팅 그룹

카나리 배포를 성립시키려면 트래픽을 쪼개주는 라우팅 계층(Load Balancer, API Gateway, Service Mesh 등)이 필수이다.

타겟팅 기준(누구에게 먼저 보여주냐?)

- 트래픽 비율 기준 : 전체 요청의 1% → 5% → 25% → 50% → 100%단계별 확대
- 특정 사용자 그룹(내부 직원 먼저)
    - 외부 유저에게 열기 전, 사내 임직원 계정/사내IP에만 v2신버전을 먼저 노출한다.
- 특정 지역 / 환경 기준 : 특정 국가, 특정 기기 요청만 v2로 타겟팅하여 검증한다.

버전 2 인스턴스 새로 하나 올라오고 화살표가 갈라진다.

→ 전체 요청의 10%만 v2로 보내고 나머지는 v1으로 보낸다.

→ 이 시점부터 실사용 검증이 이뤄지고, 소수의 사용자가 새로운 버전을 쓴다.

→ 첫 번째 카나리 배포할 때 10%씩 안한다. 훨씬 적은 대상으로 배포나가고 순차적으로 올린다.

→ 이후에는 구조가 같고 숫자만 바뀐다. 이상이 없으면 v2 비율 30퍼로 올리고 70퍼로 올리고 90퍼까지 올린다.

→ 90퍼까지 올려도 기존 v1은 10퍼 계속 받는다.

→ 마지막 완전 배포 이전으로 돌아갈 길이 계속 살아있다.

→ 전체 인스턴스 안에서 새로 배포 안하고 기존 인스턴스의 배포 비율을 조장하는 것도 가능하다. 블루그린처럼 완전히 동일한 것을 만드는 것이 아니다.

## 단계 확대/중단을 결정하는 모니터링 지표

- 최소 관찰 시간 : 메모리 누수나 특정 데이터가 쌓여야만 드러나는 버그를 잡기 위해서 최소 지정 시간 동안 관찰을 유지한다.
- 핵심 측정 지표
    - 오류율 : HTTP 5xx에러나 예외 발생 비율이 기존 v1 대비 치솟는지 확인
    - 응답 지연 시간(Latency) : 평균치뿐만 아니라 상위 99퍼 요청의 지연 시간을 확인하여 특정 케이스 병목 감지
    - 시스템 자원 사용량 : CPU, Memory, DB Connection 사용량이 예상 범주 내인지 확인
    - 비즈니스 보조 지표 : HTTP 응답은 정상이지만 로직 오류로 인한 현상 감지

## 카나리 배포에서의 롤백 호환성과 주의사항

- 롤백 실행 : 카나리 진행 중 지표가 악화되면, 라우팅 계층의 v2트래픽 비율을 즉시 0퍼로 수정만 하면되므로 롤백 자체는 빠르고 범위고 극소수에 그친다.
- 호환성 주의점
    - 트래픽을 0퍼로 되돌려도, v2가 돌아가는 짧으 시간 동안 DB스키마를 고쳤거나 새 포맷의 메시지큐 이벤트를 발생했다면 구버전이 이를 읽지 못해 터질 수 있음
    - 따라서 카나리 배포를 적용하더라도 데이터베이스 및 메시지 포맷의 하위 호환성 설계가 전제되어야한다.

## 정리

- 카나리 배포는 새 버전을 전체에 한꺼번에 열지 않고 실제 운영 트래픽의 일부에만 먼저 노출하고 모니터링 한 다음에 범위를 단계적으로 넓혀가는 전략
- 배포 범위 정하는 방식은 라우팅 계층을 통해서 처리할 수 있다. 비율이 아니라 사용자 그룹이나 특정 지역으로도 나눌 수 있다. 실제로는 내부 직원들을 먼저 대상으로 띄워서 진행하기도 한다.
- 다음 단계로 넓혀갈지는 미리 정해둔 관찰 시간이나 오류율, 응답지연, 자원 사용 상태 같은것을 보면서 판단을 해야한다.
- 롤백할때는 그냥 트래픽 비율만 전환해서 되는게 아니라 데이터나 이벤트 발생한게 있으면 그에 대한 것도 고려해서 호환성 있게 개발한다.
