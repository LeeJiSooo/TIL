## 설명할 수 있어야 하는 것

- 롤링 배포가 무엇을 어떤 순서로 교체하는 방식인지
- 교체할때마다 어떤 단계를 거치는지
- 어떤 위험이 있는지

## 정의와 필수 전제 조건

기존 인스턴스(EC2, Pod 등)들을 한 번에 바꾸지 않고, 일정 비율이나 개수만큼 순차적으로 새 버전으로 교체하며 전체 서비스를 점진적으로 업데이트하는 무중단 배포 전략이다.

**필수 전제 조건** 

- 다중 인스턴스 구조 : 요청을 나누어 받을 수 있는 인스턴스가 최소 2대 이상 존재해야 한다. (1대면 내리는 순간 무중단이 불가능하다.)
- 라우터 계층(Load Balancer) : 트래픽을 처리할 대상 목록(Target Group)에서 구버전을 빼고 신버전을 집어넣는 제어를 반복해 주는 로드 밸런서가 필수적이다.

## 인스턴스 1대를 교체할 때 거치는 단계

새 버전으로 1대를 바꿀 때마다 아래 절차가 굴러가듯 반복된다.

1. 라우팅 조정(목록에서 제외)
2. 신버전 실행(v2 앱 구동)
3. Health Check(수신 준비 확인)
4. 트래픽 투입(Target Group 추가)
5. Connection Draining(구버전 남은 요청 대기)

**커넥션 트레이닝**

구버전 인스턴스를 로드 밸런서에서 뺐다고 즉시 종료하면, 기존에 처리 중이던 유저의 요청이 차단되어 에러가 발생한다. 따라서 기존 요청이 완료될 때까지 지정된 시간(대기 시간)동안 기다린 후 프로세스를 안전하게 중료해야 한다.

웹소켓 같은 지속 연결은 대기 시간으로 해결되지 않으므로 클라이언트 재연결 로직을 함께 구현해야 한다.

## 롤링 배포의 실행 방식

#### In-Place(제자리 교체 방식)

기존 실행 중인 v1 인스턴스 1대를 먼저 내리고(종료), 그 빈자리에 v2 인스턴스를 올려서 채우는 제자리 교체 방식이다.

<img width="2202" height="1398" alt="image" src="https://github.com/user-attachments/assets/9d3b8cb3-23ae-4826-bbb3-16d177c1d453" />


→ 전체 인스턴스 개수는 그대로 두고 진행하는 방식이다. 추가 자원을 안 쓴다.

→ 제일 위에 있는 인스턴스 로드 밸런서 대상 목록에서 빼고 처리중인 요청 정리한 다음에 종료한다.

→ 요청 받는 인스턴스가 한대 줄었다. 서비스는 계속되는데 처리할 수 있는 용량이 줄어든 상태

<img width="1994" height="1470" alt="image" src="https://github.com/user-attachments/assets/45c824d8-6c3d-4b7f-a916-14aa599914de" />


기존 v1인스턴스를 내리지 않고, 옆에 v2인스턴스를 먼저 새로 띄운 후(헬스체크 완료), 기존 v1인스턴스 1대를 내리는 방식이다.

→ 인스턴스 실행했으면 확인하고 통과한 다음에 대상 목록에 들어가서 요청을 받기 시작한다.

→ 이 시점에서 중요한 건 v1인스턴스랑 v2인스턴스가 동시에 요청받는다.

→ 전체 인스턴스 교체가 끝날때까지, 구버전이랑 신버전이 같이 사용자 요청을 처리하는 구간이 생긴다.

→ 그래서 두 버전이 잠깐 공존해도 서로 깨지지 않게 만들어야 한다.

→ 응답 형식이 바뀌었다고 하면 프론트엔드에서 두 형태 모두 처리될 수 있게 만들어야 한다.

→ 사용자의 로그인 상태 같은 세션 정보가 한쪽 버전에서만 통하면 요청이 다른 버전으로 갈 때 문제가 생긴다.

→ DB 저장되는 형태도 마찬가지이다.

→ 이런 호환성을 배포 도구 측면이 아니라 개발할때 챙겨야하는 조건

<로그인 세션>

위와 같이 롤링 배포하면서 로그인 세션에 생길 수 있는 문제를 막기 위해선 어떻게 해볼 수 있을까?

→ 로그인 상태 같은 세션 정보를 인스턴스 메모리에 들고 있으면 인스턴스가 교체되는 순간에 사용자가 로그아웃될 수 있으니까 레디스 같은 별도의 공용 저장소에서 관리하면 된다.

→ 어떤 인스턴스로 요청이 가던간에 레디스를 바라보고 있어서 사용자는 변화를 느끼지 못한다.

<img width="2068" height="1512" alt="image" src="https://github.com/user-attachments/assets/23fcf434-f258-4d3b-ba6a-65a21fe891cc" />


하다 보면 남은 인스턴스들도 같은 순서 반복하면서 교체 진행한다.

#### Side-by-side(동시 실행 방식)

기존 v1 인스턴스를 내리지 않고, 옆에 v2 인스턴스를 먼저 새로 띄운 후(헬스체크 완료), 기존 v1 인스턴스 1대를 내리는 방식이다. 

<img width="1728" height="1324" alt="image" src="https://github.com/user-attachments/assets/01c37d2e-c26f-4bac-a3b3-600238a2563c" />


v1을 하나도 내리지 않은 상태에서 새로운 v2인스턴스를 실행했다.

→ 배포전보다 인스턴스 한대 늘어난 상태. v2헬스체크 통과하면 그때 돌아간다.

→ 여기서 인플레이스랑 차이. 인플레이스는 하나 내려야 하나 올리는데, 여기는 내리기 전에 먼저 올린다.

→ 그 대신에 자원이 추가적으로 필요하다.

<img width="2130" height="1444" alt="image" src="https://github.com/user-attachments/assets/c15c65aa-0d42-4a26-957d-9a74c7df6b15" />


새로운 인스턴스가 요청을 정상적으로 받고 있는게 확인이 되면 이제 기존 v1인스턴스 중 하나를 대상 목록에서 빼고 처리중인 요청 정리하고 내린다.

→ 처리 용량면에서는 유리하다.

→ 새 인스턴스를 먼저 올리고 기존 인스턴스를 내리니까 배포중에도 요청을 받은 인스턴스 수가 원래보다 떨어지는 구간이 없다.

→ 인플레이스는 하나 내리면 새로운 인스턴스 준비될때까지 잠깐 낮아지는 구간이 있다.

이런 과정을 반복해서 v2는 늘고 v1은 줄어든다

→ 전체가 v2로 바뀌고 로드밸런서는 v2로만 요청을 보낸다.

롤백할 때

→ 새 인스턴스를 올리고 나서 기존 인스턴스를 내리는 방식이라서 배포가 진행중인 시점에 아직 내리지 않은 v1인스턴스가 그대로 살아 있는 경우가 된다.

→ 그래서 문제가 발견되면 그냥 남아 있는 v1 인스턴스가 요청 받게하면 된다.

In-Place와 Side-by-Side 비교

| **비교 항목** | **In-Place (제자리 교체)** | **Side-by-Side (동시 실행)** |
| --- | --- | --- |
| **추가 자원 필요 여부** | **없음** | **있음** (교체 단위만큼 임시 증가) |
| **배포 중 처리 용량** | 일시적으로 감소 구간 발생 | 원래 용량 이상으로  유지 |
| **배포 완료 시간** | 상대적으로 느림 (내리고 띄움) | 상대적으로 빠름 (미리 띄움) |
| **초기 롤백 대응** | 구버전을 다시 띄워야 해서 느림 | 기존 구버전이 살아있어 빠른 편 |

## 롤링 배포 시 개발자가 챙겨야 할 요소(버전 혼재)

롤링 배포가 진행되는 동안에는 v1과 v2인스턴스가 트래픽을 동시에 나누어 받아내는 ‘버전 공존 구간’이 존재한다.

```
								┌─► [ EC2 #1 (v1 구버전) ] ──► 구버전 응답 생성
 [ 유저 트래픽 ] ──┼─► [ EC2 #2 (v2 신버전) ] ──► 신버전 응답 생성
 (Load Balancer)└─► [ EC2 #3 (v1 구버전) ] ──► 구버전 응답 생성
```

- 로그인 세션 파편화 위험
    - 유저가 v1서버에서 로그인하여 세션을 서버 메모리에 저장했는데, 다음 요청이 v2 서버로 전달되면 세션을 찾지 못해 갑자기 로그아웃 현상이 발생한다.
    - 해결책 : 세션 정보를 EC2 인메모리가 아닌 Redis같은 중앙 공용 저장소에서 관리하여 어느 서버로 가든 세션이 유지되도록 설계한다.
- API 및 DB 호환성
    - 응답 JSON 구조가 변경되거나 DB컬럼명이 바뀌더라도, 프론트엔드와 백엔드가 v1,v2 응답을 모두 처리할 수 있도록 하위 호환성을 유지하며 코드를 작성해야 한다.

| **비교 항목** | **롤링 배포 (Rolling)** | **블루/그린 배포 (Blue/Green)** |
| --- | --- | --- |
| **배포 방식** | 기존 그룹 안에서 **일부씩 순차적 교체** | 완벽히 독립된 **신규 환경을 통째로 띄워 한 번에 전환** |
| **자원 부담** | **적음** (추가 비용 없음 ~ 최소한) | **큼** (환경이 2배 필요하므로 비용 발생) |
| **버전 공존 유무** | **있음** (배포 중 v1, v2가 동시에 켜져 있음) | **없음** (라우터 스위치로 완벽 분리) |
| **롤백 복잡도** | 이미 교체된 서버들을 역순으로 되돌려야 함 | 라우터 스위치만 되돌리면 되므로 1초 만에 완료 |

## 정리

- 롤링 배포는 요청을 처리하는 인스턴스가 여러개인 서비스에서 한번에 다 바꾸지 않고 일부 새버전으로 교체해나가는 무중단 배포 전략이다.
- 라우팅 계층이 있어야 하고, 요청 대상 그룹에 포함시키고 제외하는 작업을 반복적으로 해줘야 한다.
- 교체순서는 큰 틀에서 인스턴스 대상 목록을 조정하고 새버전 실행하고 헬스체크 확인하고 그 다음에 요청을 받게한다. → 그후에 구버전 정리한다.
- 인플레이스 : 인스턴스 자리 비우고 그 자리에 새로운 버전을 채워서 추가 자원이 필요 없지만 배포중 처리 용량이 잠깐 낮아지고 시간이 걸린다.
- 사이드 바이 사이드 : 새것을 먼저 올리고, 기존것을 내려서 자원을 잠깐 더 쓰지만 용량 지키기 쉽고 첫 롤백 대응도 빠르다.
