## 설명할 수 있어야 하는 것

- 워크플로우를 이루는 구성요소가 각각 무슨 책임을 지는가?
- 검증된 결과물이 어떤 경계를 넘어서 배포 대상까지 도달하는가?
- 중간에 실패하면 어디서 멈추는가?

## 정의와 특징

GitHub 저장소 내에서 코드의 빌드, 테스트, 배포 등의 워크플로우를 자동화하는 GitHub 공식 CI/CD 도구

**왜 깃허브 액션을 쓸까?**

- 저장소 밀착형(IaC) : 별도의 외부 CI/CD 서버를 띄울 필요 없이, 내 프로젝트 코드의 .github/workflows/*.yml 파일 하나로 파이프라인을 관리가 가능하다.
- 이벤트 연동성 : 코드가 push되거나 PR이 열리는 지점(저장소)과 자동화 도구가 같은 공간에 존재하여 연동 거리가 짧다.

## GitHub Actions를 구성하는 핵심 요소

```
[ Event: git push 발생]
        │
        ▼ (워크플로우 깨움)
[ Workflow: .github/workflows/deploy.yml ]
        │
        ├─► [ Job 1: Build & Test ] ──► (Runner: Ubuntu 가상 환경)
        │      ├─ Step 1: Action (actions/checkout@v4 - 코드 가져오기)
        │      ├─ Step 2: Action (actions/setup-java@v4 - JDK 설치)
        │      └─ Step 3: Run    (./gradlew test - 테스트 명령어 직접 실행)
        │
        └─► [ Job 2: Deploy ]       ──► (Runner: Ubuntu 가상 환경)
               └─ Step 1: Run    (docker build & push - ECR 업로드)
```

- 이벤트 : 자동화 파이프라인을 트리거(시작)하는 사건. (push, pull_request, schedule)
- 워크플로우 : 이벤트 발생 시 실행할 전체 자동화 흐름의 최상위 단위(.yml 파일). 프로젝트당 여러 개 존재 가능
- Job(잡) : 워크플로우 안에서 독립적으로 실행되는 작업 단위 → 각 Job은 독립된 실행 환경(Runner)을 할당받음
- Runner(러너) : Job이 실제로 격리되어 돌아가는 가상 서버/컴퓨터
- Step(스텝) : 하나의 Job 내부에서 위에서 아래로 순차적으로 실행되는 개별 단계
- Action(액션) : 반복되는 흔한 작업(코드 가져오기, JDK 설치 등)을 플러그인처럼 재사용할 수 있게 만들어둔 공개 오픈소스 조각

→ 이벤트가 워크플로우를 깨우면, 내부의 Job들이 각자의 Runner에 구동되며, Job 안의 Step들이 순서대로 Actions을 호출하거나 명령을 직접 실행한다.

## 파이프라인 실행 중 발생하는 경계와 흐름

CI/CD파이프라인이 진행될 때 데이터와 주도권이 어떤 경계를 넘어가며 전달되는지 알기

```
[ 1. GitHub 저장소 ] ──(Event 발생)──► [ 2. GitHub-hosted Runner ]
                                                    │
                                     (도커 이미지 빌드 완료 후)
                                                    │
 [ 4. 운영 EC2 서버 ]  ◄──(Deploy 명령)── [ 3. AWS ECR 레지스트리 ]
   (실제 사용자 서빙)                       (독립된 불변 결과물 보관)
```

1. 검증 단계(Runner 내부) : GitHub가 준비해 준 러너(격리 컴퓨터)로 코드를 받아와 테스트 및 컴파일 수행
2. 결과물 저장 경계(Runner → Registry) :
    - 러너는 작업이 끝나면 메모리와 파일이 완전히 삭제 되는 임시 서버이다.
    - 따라서 빌드된 도커 이미지를 러너에 두면 안 되고,  AWS ECR같은 레지스트리로 push 하여 독립된 저장소로 넘겨야 한다.
3. 배포 반영 경계(Registry → EC2) :
    
    GitHub Runner의 역할이 끝나고, 실제 우리가 운영하는 EC2 서버로 접속하여 레지스트리에서 이미지 pull 받아서 컨테이너를 구동시킨다.
    

## 파이프라인 실패 및 안전장치(의존성 제어)

- Job간 의존성(needs)
    - GitHub Actions에서는 Job들이 기본적으로 병렬(동시)로 실행된다.
    - 따라서 배포 Job이 테스트 Job보다 먼저 실행되면 안되므로 `needs: build-and-test`처럼 **의존 관계를 선언**해야 한다.
- 실패 시 즉시 중단
    - 앞선 Job(테스트)이 하나라도 실패하면 뒤쪽의 Job(배포)은 실행되지 않고 파이프라인 전체가 그 자리에서 중단된다.
    - 이를 통해 검증되지 않은 에러 코드가 운영 서버로 흘러 들어가는 것을 완전 차단한다.
 
## 정리

- 깃허브 액션은 CI/CD 그 자체가 아니라 프로세스를 구현하는 대표적인 도구 중 하나이다.
- 코드 저장하는 곳이랑 밀착되어 있다는 것이 특징이다.
- 이벤트가 워크플로우를 깨우고, 워크플로우 안의 잡들이 각자 러너에서 실행되고 잡 안의 스텝들이 명령을 실행하거나 액션을 불러온다.
- 워크플로우 자체에 대한 정의랑 이벤트 관리는 깃헙이 맡고, 실제 실행은 러너가 맡는다.
- 흐름은 검증, 결과물 생성과 보관, 대상 환경에 반영으로 이어져있다. 결과물을 레지스트리 거치면서 파이프라인이랑 독립적인 존재가 되고 대상 환경에 반영한다.
