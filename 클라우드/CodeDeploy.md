## 설명할 수 있어야 하는 것

- 코드 디플로이가 파이프라인 전체가 아니라 어느 부분을 담당하는지
- 그 담당하는 부분 안에서 어떤 구성요소가 어떤 책임을 맡는지

## 정의와 흐름 속 위치

EC2, 온프레미스 서버, AWS Lambda, ECS 등의 실행 환경으로 애플리케이션 배포과정을 자동화해주는 AWS 전용 배포 실행 서비스

코드디플로이가 코드를 올릴 수 있는 대상은 한 종류가 아니다. EC2 위에도 올릴 수 있고, AWS 밖에 있는 온프레미스에도 올릴 수 있고, 서버리스 환경에 람다라는 것에도 올릴 수 있다.

AWS Lambda : 서버를 직접 띄우지 않고 코드만 올려서 실행하는 방식

**전체 파이프라인에서의 위치**

- CI/CD 파이프라인 전체를 지휘하는 도구(GitHub Actions)가 빌드 및 테스트(CI)를 마치고, 완성된 배포 묶음(Artifact / 도커 이미지 등)을 저장소(S3 / ECR)에 올려둔 ‘그 이후의 순간’부터 개입한다.
- CI/CD를 대체하는 것이 아니라, CD 파이프라인의 ‘배포 실행 단계’를 전문적으로 위임받아 수행하는 보완적 관계이다.

[GitHub Actions / Jenkins]

-코드 검증(CI)

-빌드 & 테스트

[AWS S3/ ECR]

-배포 묶음 보관

[AWS CodeDeploy]

-배포 지시 & 상태 관리

-롤백 및 진행률 제어

[Target EC2 Group]

-Agent가 다운로드 후 애플리케이션 구동

## 왜 GitHub Actions 스크립트 대신 CodeDeploy를 쓸까?

| **구분** | **GitHub Actions / Jenkins 직배포** | **AWS CodeDeploy 활용 배포** |
| --- | --- | --- |
| **배포 방식** | CI 러너가 운영 EC2에 **SSH 접속하여 명령을 직접 밀어 넣음 (Push 방식)** | EC2 내부의 **Agent가 주기적으로 CodeDeploy에 지시를 물어보고 가져옴 (Pull 방식)** |
| **보안성** | EC2의 SSH 22번 포트를 외부(CI 러너)로 열어두어야 함 | 외부 진입 포트를 열 필요 없이 **AWS IAM 권한만으로 안전하게 배포** 가능 |
| **서버 확장성** | 서버가 10대로 늘어나면 배포 스크립트 내 IP 목록을 사람이 일일이 수정해야 함 | **EC2 태그(Tag) 기준**으로 배포 그룹을 관리하므로, 서버가 늘어나도 자동 적용됨 |
| **상태 및 롤백** | 스크립트로 상태 체크, 배포 진행률, 롤백 로직을 직접 복잡하게 구현해야 함 | AWS 콘솔에서 **서버별 배포 진행 상태를 시각화**하고 **실패 시 자동 롤백(Rollback)** 제공 |

## CodeDeploy의 구성요소

<img width="2282" height="1228" alt="image" src="https://github.com/user-attachments/assets/9ace4ece-b256-4741-bf87-3054ace13146" />


1. 배포 묶음 (Revision) → S3/ECR에 저장된 빌드 결과물 + appspec.yml 지시서
2. 배포 그룹 (Deployment Group) → 태그(Name=Prod-Web)로 묶인 EC2 인스턴스들의 집합
3. AppSpec 파일 (appspec.yml) → 파일 배치 경로 및 배포 단계별 실행 스크립트 정의
4. CodeDeploy Agent → EC2 내부에서 배포 명령을 수신·실행하는 일꾼

#### CodeDeploy Agent의 배포 지시 확인

EC2 내부의 Agent가 CodeDeploy서비스에게 “나에게 온 새 배포 지시가 있는가?”를 폴링하여 확인하다.

#### 배포 묶음 다운로드

새 배포가 생성되면 Agent가 S3 또는 ECR에서 배포 묶음 및 appspec.yml지시서를 내려받는다.

#### Appspec 훅 순차 실행

appspec.yml에 적힌 순서에 따라 기존 앱 중지 → 파일 복사 → 신규 앱 시작 → 헬스체크를 실행한다.

#### 성공/실패 상태 리포트

Agent가 실행 결과를 CodeDeploy 서비스 본체로 보고한다. 실패 감지 시 설정에 따라 즉시 이전 버전으로 자동 롤백된다.

## CodeDeploy가 지원하는 대표적인 무중단 배포 전략

운영중인 서비스가 중단되지 않도록 두가지 배포 전략을 자체적으로 제어해준다.

1. **롤링 업데이트**
- 동작 : 기존 서버 그룹 안에서 서버를 1대(또는 일정 비율)씩 트래픽 분산 대상에서 빼낸 뒤, 새 버전을 올리고 다시 투입하는 과정을 반복한다.
- 장점 : 추가 서버 비용이 들지 않는다.
- 단점 : 배포 진행 중에 구버전과 신버전이 동시에 켜져 있어 유저에 따라 서로 다른 응답을 받을 수 있는 상태가 발생한다.

<img width="2132" height="1434" alt="image" src="https://github.com/user-attachments/assets/e8426af1-13c3-46a5-8a13-96906df9bb38" />


1. **블루/그린 배포**
- 동작 : 현재 구버전이 도는 환경(Blue)과 동일한 크기의 신버전 환경(Green)을 따로 띄운 후에, 신버전 검증이 끝나면 로드 밸런서의 트래픽 스위치를 한 순간에 Green으로 전환한다.
- 장점 : 구버전과 신버전의 혼재가 없고, 문제가 생기면 스위치만 다시 Blue로 되돌리면 되므로 롤백 속도가 극도로 빠르고 안전하다.
- 단점 : 배포 순간 동안 두 배의 서버 자원을 띄워야 하므로 비용이 더 발생한다.

## 정리

- 코드 디플로이는 배포를 자동으로 수행해주는 AWS 관리형 서비스
- CI/CD 흐름 안에서 검증이 끝난 뒤에 배포 실행 단계를 하나씩 맡아서 처리한다.
- 깃헙 액션이랑은 다른 영역을 맡아서 담당한다. 코드 디플로이는 어느 배포 대상 서버에 어디까지 올라갔는지 관리하고 모니터링한다. 깃헙액션 같은 도구랑 다체 관계가 아니라 보완 관계에 가깝고 배포 영역을 누가 처리하느냐의 차이다.
- 빌드 결과물이 배포 묶음이 되어서 저장소에 올라가도 코드 디플로이는 어떤 배포 그룹에 어떤 방식으로 배포할지 지시하고 각 서버의 에이전트가 그 지시를 실행하고 결과를 보고한다.
