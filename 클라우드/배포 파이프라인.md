## EC2 직접 배포(빅뱅 배포)

<img width="1474" height="672" alt="image" src="https://github.com/user-attachments/assets/569d1ea8-bb59-45c0-8e83-543b63cf1f01" />


`Developer push` ➔ `EC2 git pull (수동)` ➔ `서버 직접 실행` ➔ `User` 

개발자가 직접 EC2 서버에서 SSH접속해서 최신 코드를 git pull 받고, 서버를 껐다 켜며 수동으로 배포하는 가장 기초적인 방식

- 장점 : 구성 요소가 적고 구조가 매우 단순하다.
- 단점 및 해결과제 :
    - 사람이 직접 조작하므로 실수할 가능성이 존재한다.
    - 서비스 중단 : 코드를 받고 다시 띄우는 동안 서버가 꺼져 있어야 한다.
    - 환경 불일치(”내 컴퓨터에서는 되는데 서버에서는 안 된다”) : EC2에 설치된 자바 버전이나 라이브러리 환경에 따라 실행 여부가 달라진다.

## Docker + Nginx 배포(단일 인스턴스)

<img width="1538" height="624" alt="image" src="https://github.com/user-attachments/assets/5dea7073-dfa9-4820-9757-25db6ff1d8d3" />


`Dev push` ➔ `Docker 이미지 빌드` ➔ `Docker Hub push` ➔ `EC2에서 Image pull` ➔ `컨테이너 실행 & Nginx 연결` 

- 애플리케이션과 실행 환경(자바 버전, OS 설정 등)을 한 덩어리의 ‘이미지’로 포장하여, 보관 창고인 ‘레지스트리(Docker Hub)’에 올리고 EC2는 이를 받아서 실행한다.
- 해결된 점(어디서나 일관된 실행 환경) :
    - 서버에 자바 등을 설치할 필요가 없다.
    - 포장된 결과물(이미지)을 그대로 실행하므로, 개발자 로드/검토자 환경/운영 서버 모두 동일한 실행 환경이 보장된다.
- 단점 및 해결 과제 :
    - 챙겨야 할 컨테이너(App, Nginx 등)이 늘어나면서 서버에서 각각 손수 실행하고 묶어주는 수동 작업의 부담이 남아있다.

## Dockerk Compose + Nginx(단일 인스턴스)

<img width="1592" height="584" alt="image" src="https://github.com/user-attachments/assets/4cd2599f-9214-4733-a091-f33e4b18147e" />


`docker-compose.yml 작성` ➔ `EC2에서 docker-compose up -d` ➔ `Nginx & App 컨테이너 일괄 실행`

- 서비스 구성에 필요한 여러 컨테이너(App, Nginx, Redis 등)의 연결 관계와 실행 조건들을 docker-compose.yml이라는 하나의 파일에 명시적으로 선언한다.
- 해결된 점(설정의 코드화 및 재현성) :
    - 사람이 머릿속으로 기억하던 복잡한 명렁어/구성을 파일(코드)로 옮김
    - 어제 띄운 것과 오늘 띄운 것, 내 맥북과 동료 맥북, EC2 서버 환경을 똑같이 재생성(재현)할 수 있고 예측 가능해짐
- 단점 및 해결 과제 :
    - 여전히 docker-compose up 명령어를 사람이 SSH 접속해서 직접 실행해야 하므로 완전한 자동화가 아니다.

## CI/CD 파이프라인 구축(GitHub Action, 단일 인스턴스)

<img width="1530" height="776" alt="image" src="https://github.com/user-attachments/assets/86a07b26-6d5c-4107-aacd-e954673ec153" />


`Dev git push` ➔ `GitHub Actions 트리거` ➔ `자동 빌드/테스트` ➔ `Docker Hub 푸시` ➔ `EC2 자동 SSH 접속 & 배포`

- 사람이 배포 버튼을 누르는 것이 아니라, “코드가 GitHub에 반영되었다”는 사건이 자동으로 배포 흐름을 시작한다.
- CI(지속적 통합) : 코드 변경 사항을 자동으로 빌드하고 테스트 코드를 돌려 검증한다.
- CD(지속적 배포) : 검증을 통과한 코드를 이미지로 만들어 레지스트리에 푸시하고, EC2 배포까지 자동으로 한다.
- 해결된 점(검증과 배포의 자동화) :
    - 사람의 시간을 절약하고 생산성을 대폭 향상시킨다.
    - 파이프라인이 정해진 순서로만 진행되므로 배포의 일관성과 추적 가능성(누가, 언제, 무엇을 배포 했는지 기록 남음)이 확보된다.
- 단점 및 해결 과제 :
    - 단일 인스턴스 특성상, 컨테이너를 내렸다가 올리는 짧은 배포 공백이 물리적으로 존재한다.

## 무중단 배포(Blue/Green 파이프라인, 다중 인스턴스)

`CI/CD 통과` ➔ `새 버전을 Green 환경에 별도 배포` ➔ `Green 헬스체크(정상 확인)` ➔ `Nginx 트래픽을 Blue에서 Green으로 전환`

- 기존에 사용자 요청을 받던 서버 환경을 Blue, 새 버전을 미리 올려두는 서버 환경을 Green으로 분리하여 다중 인스턴스로 운영한다.
- 해결된 점:
    - 무중단 운영 : Green에 새 버전을 올리고 정상 작동하는지(헬스체크)우리가 먼저 확인한뒤, Nginx의 바라보는 방향(Reverse Proxy)을 한 번에 스위칭하여 사용자 끊김을 완전히 없앤다.
    - 롤백 경로 확보 : 스위칭 후 신규 버전(Green)에 장애가 발생하면, 즉시 트래픽을 이전 버전인 Blue로 다시 돌려 손쉽게 복구 가능하다.
- 트레이드오프 :
    - 두 개의 서버 환경을 동시에 유지해야 하므로 서버 자원(비용)이 2배로 들고 관리가 복잡해진다. DB데이터 동기화 문제 등도 함께 고려해야 한다.

| **단계** | **배포 주체** | **실행 환경 일관성** | **배포 중단(다운타임)** | **주요 특징 & 이점** |
| --- | --- | --- | --- | --- |
| **1. EC2 직접 배포** | 수동 (사람) | ❌ 불일치 (서버 환경에 의존) | O (필수 중단) | 구조가 단순함 / 휴먼 에러 발생 위험 |
| **2. Docker** | 수동 (사람) | ⭕ 일관됨 (이미지로 포장) | O (필수 중단) | 내 컴퓨터와 서버의 환경 차이 극복 |
| **3. Docker Compose** | 수동 (사람) | ⭕ 완벽 일관 (파일로 선언) | O (필수 중단) | 복수 컨테이너 구성을 코드 한 줄로 실행 |
| **4. CI/CD** | **자동 (파이프라인)** | ⭕ 완벽 일관 | O (찰나의 다운타임) | Push만 하면 빌드·테스트·배포 자동화 |
| **5. Blue/Green** | **자동 (파이프라인)** | ⭕ 완벽 일관 | **❌ 없음 (무중단)** | 트래픽 전환을 통한 무중단 및 즉시 롤백 가능 |

## 용어 정리

- EC2 - AWS에서 빌려 쓰는 가상 서버(스프링 애플리케이션이 실제 실행되는 환경)
- Docker - 앱과 실행 환경을 하나로 포장(이미지화)하여 어디서든 동일하게 돌리는 기술
- Registry(Docker Hub) - 포장된 Docker 이미지를 저장하고 관리하는 중앙 창고
- Nginx - 맨 앞단에서 사용자 요청(API Call)을 받아 뒤쪽 앱 서버로 넘겨주는 웹 서버(리버스 프록시)
- Reverse Proxy - 클라이언트 요청을 대리로 받아 내부 서버로 전달하고 제어하는 역할
- CI/CD - 빌드/테스트를 자동 검증(CI)하고, 그 결과물을 실제 운영 서버에 자동 반영(CD)하는 흐름
