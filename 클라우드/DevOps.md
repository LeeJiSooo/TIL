## DevOps의 정의

개발과 운영의 협업을 통해 소프트웨어의 배포 속도와 안정성을 동시에 높이는 문화이자 방법론

- 도구나 직무의 이름이 아니다 : 설치해서 쓰는 프로그램이나 특정 사람만의 직무를 뜻하는 게 아니다.
- 일하는 방식이자 문화 : “어떻게 개발과 운영을 연결하여 빠르고 안전하게 서비스를 사용자에게 전달할 것인가?”에 대한 조직적인 해결방식
- 책임의 역할(로그인 기능) :
    - 개발(Dev)영역 : 로그인 기능 코드 작성 → 동작 확인 → 배포 가능한 상태로 준비
    - 운영(Ops)영역 : 준비된 코드를 실제 서버에 반영 → 모니터링 → 문제 발생 시 대응 및 유지보수
    - DevOps의 역할 : 이 두 책임 사이가 끊기지 않고 매끄럽게 이어질수록 수동 벽을 없애는 것

## 등장 배경(개발 vs 운영의 구조적 갈등)

옛날 방식처럼 개발팀과 운영팀의 역할이 분리되어 있으면, 두 팀이 바라보는 목표가 서로 반대가 되는 문제가 발생한다.

[개발팀]

목표 : 새로운 기능을 “빠르고/자주” 배포

성과 : 신규 기능 출시 속도

[운영팀]

목표 : 서비스의 “안정성”유지(변화 최소화)

성과 : 시스템 무장애

**문제점**

- 개발이 넘긴 결과물을 운영팀이 이해하고 수작업으로 배포하느라 시간이 오래 걸린다.
- 휴먼 에러 : 사람이 직접 서버에 접속해서 커맨드를 치고 설정하다 보니 순서를 빠뜨리거나 실수한다.
- 책임 회피 및 복구 지연
    - 상황 : 배포 직후 로그인 장애 발생
    - 개발팀 : 개발 환경에서는 잘 됐는데? 운영 서버 설정이나 환경 문제가 아닌가?
    - 운영팀 : 서버 바귄 것 없다. 코드 버그 아닌가?
    - 결과 : 문제 원인을 찾는 데 오래 걸리고, 복구가 늦어져 사용자가 이탈한다.

## DevOps가 문제를 해결하는 방식

데브옵스는 “개발과 운영은 별개가 아니라 빠르고 안정적인 배포라는 하나의 목표를 가진 팀이다”라는 관점에서 출발

**문화적 변화 : 공통 책임**

- 개발자는 코드만 짜고 던져버리는 게 아니라 배포와 운영 안정성까지 고려한다.
- 운영자는 개발자가 쉽게 배포할 수 있는 자동화된 인프라 판을 깔아준다.

**기술적 변화 : 자동화(CI/CD & IaC)**

사람의 손에 의존하던 수작업을 코드가 대신 처리하도록 자동화 파이프라인을 구축함

- CI/CD : 개발된 코드를 자동으로 통합/빌드/테스트(CI), 검증된 코드를 실제 운영 환경까지 자동으로 배포(CD)한다.
- IaC(Infrastructure as Code - 코드로서의 인프라) :
    - 서버 생성, 네트워크(VPC), 보안 그룹 설정 등 인프라 구성을 AWS 콘솔에서 사람이 클릭해서 만드는 게 아니라 ‘코드’로 작성하여 관리하는 방식
    - 장점 : 사람이 클릭할 때 생기는 실수를 방지하여 언제든 똑같은 환경을 재현할 수 있고, 인프라 변경 이력이 GitHub 커밋 기록으로 남음

| **구분** | **주요 책임** | **핵심 목표** |
| --- | --- | --- |
| **개발 (Dev)** | 기능 설계, 코드 구현, 지속적 통합(CI), 빌드 및 테스트 검증 | 빠른 기능 출시 및 코드 품질 확보 |
| **운영 (Ops)** | 인프라 구성(IaC), 모니터링, 안정성 유지, 지속적 배포(CD) | 시스템 안정성 및 다운타임 최소화 |
| **DevOps** | 개발과 운영 사이의 수작업 및 벽을 허물고 **CI/CD 자동화**로 연결 | **배포 속도 향상 + 서비스 안정성 확보 (생산성 극대화)** |

## 정리

- 데브옵스는 개발이랑 운영을 연결해주는 문화, 방법론
- 개발이랑 운영이라고하는 영역이 빠르고 안정적인 배포라는 공동의 목표를 향해서 나아가는 방식
- 개발 영역은 기능 설계하고 만들어서 자주 통합하고 검증하고 배포 가능한 상태까지 준비하는 쪽
- 운영 영역은 결과물을 실제 서비스 환경에서 배포하고 인프라 관리하고 모티터링 하면서 안정적으로 유지하는 쪽
- 이 두 영역을 자동화로 이어주는 축이 CI/CD
