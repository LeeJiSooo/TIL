앞의 두 패턴은 객체 자체를 어떻게 다룰지에 대한 이야기

지금 배우는 내용은 객체를 어떻게 만들고 다루느냐가 아닌 객체에 어떻게 접근하느냐를 설계하는 패턴

## 가져가야 할 핵심

- 프록시 패턴이 무엇인가 - 실제 객체 앞에 그 객체와 똑같은 인터페이스를 가진 대리 객체를 하나 세우는 구조
- 이 패턴이 어떤 문제를 해결하는가 - 다른 관심사를 가진 처리가 실제 객체 안에 섞여 들어가면 본래 기능이 오염되는 상황
- 어떤 책임을 어떤 객체로 나누는가 - 실제 객체는 본래 기능만 갖고 프록시는 접근 정책만 가져간다는 분리를 설명할 수 있어야 한다.
- 비슷해보이는 것과 구분 - AOP, 필터, 인터셉터

## 정의

실제 객체에 대한 접근을 대리 객체가 제어하여, 호출 전후에 공통 처리(로깅, 보안 등)나 접근 통제(캐싱, 권한 등)를 삽입하도록 설계하는 객체지향 디자인 패턴

→ 클라이언트(호출하는 쪽)는 자신이 진짜 객체를 직접 부르고 있다고 믿는다.

→ 하지만 실제로는 그 앞에 가로막고 서 있는 대리 객체(프록시)를 호출한다.

→ 이게 가능한 이유는 프록시가 실제 객체와 완전히 똑같은 인터페이스를 구현하고 있어서 타입 관점에서 클라이언트를 속일 수 있기 때문이다.

→ 실제 객체에 코드를 더 추가해서 문제를 푸는 게 아니라, 실제 객체 앞단에 제어 지점을 하나 더 두는 방식

→ 실제 객체는 자기 비즈니스 로직에만 집중하고, 접근할 때 필요한 부가적인 관심사는 프록시가 전담하여 책임을 분리

## 사용 이유

객체 접근 시점에 공통 제어 로직을 끼워 넣어 실제 객체를 수정하지 않고도 접근 통제와 부가 처리를 일관되게 적용하기 위해서이다.

→ 기능 구현하다보면 기능 자체를 만드는 것보다 그 기능에 접근하는 과정에서 반복적으로 해야하는 처리가 자주 생길 수 있다.

```java
public void processOrder(Order order) {
    checkPermission();               // 호출 전 권한 확인
    logStart();                      // 시작 시점 로깅
    
    if ( cacheExists(order) ) {        // 캐시 존재 여부에 따른 흐름 분기
        return getFromCache(order);  // 캐시 적중 시 실제 로직 없이 조기 반환
    }
    
    doBusinessLogic(order);          // 이 메서드의 본래 책임
    logEnd();                        // 종료 시점 로깅
}
```

→ 중요한 주문 처리 비즈니스 로직은 한 줄인데, 권한/로깅/캐시 같은 다른 관심사 코드가 가로막고 있다. 

→ 캐시 확인 코드는 비즈니스 로직을 실행할지 말지 흐름 제어도 가지고 있다.

→ 정책이 바뀔 때마다 비즈니스 코드를 고쳐야 하므로 코드가 오염된다.

해결책 : 변하지 않는 “주문 처리 본래 기능”과 자주 바뀌는 “접근 정책/부가 기능”을 완전히 떼어내어 부가 기능을 프록시 객체 안으로 넣는다.

## 사용방법

#### 공통 인터페이스 정의

프록시와 실제 객체가 같은 계약을 공유해야한다.

→ 클라이언트가 “나는 실제 객체를 호출하고 있다”라고 믿는 상태를 유지하려면 둘의 타입이 완전히 같아야 한다.

→ 그 공통 타입이 인터페이스이다.

```java
public interface OrderService {
    void processOrder(String orderId);  // 클라이언트가 기대하는 공통 계약 정의
}
```

#### 실제 객체 구현

```java
public class RealOrderService implements OrderService {  // 공통 계약을 구현한 실제 객체

    @Override
    public void processOrder(String orderId) {           // 주문 처리라는 본래 기능만 담당
        System.out.println("주문 처리: " + orderId);      // 접근 정책 없이 핵심 로직만 수행
    }
}
```

→ 권한 확인이나 부가 책임은 존재하지 않는다.

#### 프록시 객체 구현

```java
public class OrderServiceProxy implements OrderService {  // 실제 객체와 동일한 계약을 구현한 프록시

    private final OrderService target;                    // 실제 일을 위임할 대상 객체 보관

    public OrderServiceProxy(OrderService target) {       // 생성자를 통한 실제 객체 주입
        this.target = target;
    }

    @Override
    public void processOrder(String orderId) {

        checkPermission(orderId);                         // 위임 전 접근 통제
        long start = System.currentTimeMillis();          // 실행 시간 측정 시작

        try {
            target.processOrder(orderId);                 // 조건 충족 시에만 실제 객체로 위임
        } finally {
            long end = System.currentTimeMillis();
            System.out.println("실행 시간(ms): " + (end - start));  // 위임 후 성능 측정 결과 출력
        }
    }

    private void checkPermission(String orderId) {        // 프록시가 가져간 접근 정책 메서드
        System.out.println("권한 확인: " + orderId);
    }
}
```

프록시는 실제 객체 앞단에서 접근 흐름을 통제하는 관문 역할을 한다.

→ 프록시도 OrderService를 구현한다. 그래서 클라이언트가 프록시를 호출하더라도 타입 관점에서는 똑같이 OrderService를 호출한다. 

→ 프록시는 실제 객체를 안에 들고 있다. 생성자로 받아서 target필드에 보관한다. targe이 진짜 일을 하는 객체이다. 프록시는 필요할때만 이 객체에게 일을 넘긴다.

→ 프록시는 위임하기 전후로 흐름에 끼어들 수 있다.

프록시가 단순한 호출 전달자가 아니라 권한 확인, 로깅, 성능 측정, 캐시, 재시도 같은 정책을 넣을 수 있다.

→ 조건이 안맞으면 실제 객체 호출을 아예 막을 수 있고, 캐시가 있으면 실제 객체를 부르지 않고 결과만 돌려줄 수 있다.

→ 프록시는 접근 정책을 적용하는 위치이다.

#### 클라이언트 호출 경로 고정

프록시가 효과를 가지려면 호출 경로가 프록시로 고정

```java
OrderService target = new RealOrderService();        // 실제 객체 생성
OrderService proxy = new OrderServiceProxy(target);  // 실제 객체를 프록시로 감싸 경로 구성

proxy.processOrder("ORDER-1");                        // 클라이언트는 프록시를 통해서만 호출
```

프록시 패턴에서는 호출이 반드시 프록시를 통과하도록 경로를 고정하는게 조건이다.

## 프록시와 혼동하기 쉬운 구조

- **MVC의 Controller** : 컨트롤러가 서비스 레이어의 비즈니스 로직을 대신 호출해 주니까 프록시라고 착각하기 쉬운데 아니다. 프록시가 성립하려면 서비스와 컨트롤러가 같은 인터페이스를 구현해서 서비스인 척 해야한다. 하지만 컨트롤러는 서비스 인터페이스를 구현하지 않고 그냥 호출만 할 뿐이다.
- 서블릿 필터 / Spring MVC 인터셉터 : 흐름 앞뒤에 끼어든다는 개념은 프록시와 같지만 책임 범위와 대상이 다르다.
    - 프록시 패턴 : ‘객체 단위’의 설계 패턴이다. 특정 클래스/객체 하나에 대한 정밀한 접근 제어를 담당한다.
    - 필터 / 인터셉터 : 웹 인프라의 구성 요소. 특정 객체를 대리하는 게 아니라, 들어오는 HTTP 요청과 응답 흐름 전체를 거시적으로 가로채는 서블릿/웹 기술 영역이다.

## 스프링부트 환경과 AOP

사람이 손으로 프록시 클래스를 짜는 일은 거의 없다.

→ 스프링이 대신 만들어준다. @Transactional

```java
@Service
public class OrderService {

    @Transactional                              // 프록시 생성을 유발하는 트랜잭션 적용 지점
    public void processOrder(String orderId) {  // 개발자는 본래 로직만 작성
        // 주문 처리 비즈니스 로직
    }
}
```

우리가 프록시 클래스를 직접 만들지 않아도, 스프링은 어플리케이션이 뜰 때 OrderService빈을 그대로 쓰지 않고, 똑같은 타입의 가짜 프록시 객체를 런타임에 동적으로 만들어 내어 가동한다.

→ 가짜 프록시가 메서드 호출 전에 Connection.setAutoCommit(false)로 트랜잭션을 대신 시작해 주고, 우리 비즈니스 로직을 중간에 위임 호출한 뒤에, 정상 종료되면 commit()을, 에러가 나면 rollback()을 대신 수행해 주는 구조이다. 

→ 먼저 나온 프록시 디자인 패턴의 아이디어를 스프링 프레임워크 차원에서 자동화 기술로 극대화한 것이 AOP이다.

**트랜잭션이 걸리지 않는 에러 상황**

```java
@Service
public class OrderService {

    // 외부에서 호출하는 일반 메서드
    public void startOrderFlow(String orderId) {
        System.out.println("일반 흐름 시작");
        
        // 문제의 구간: 같은 클래스 내의 다른 메서드를 호출 (this.processOrder()와 같음)
        processOrder(orderId); 
    }

    @Transactional // 트랜잭션은 여기에 붙어있음
    public void processOrder(String orderId) {
        // 주문 처리 비즈니스 로직
    }
}
```

왜 @Transactional이 안될까?

스프링의 모든 부가기능(`@Transactional`, `@Async`, `@Cacheable` 등)은 외부에서 들어오는 요청이 ‘스프링이 만든 프록시 객체’를 통과할 때만 발생한다.

→ 클라이언트가 orderService.startOrderFlow()를 호출하면 프록시 관문을 정상적으로 통과하긴 한다. 하지만 이 메서드에는 @Transactional가 없어 프록시는 아무것도 안 하고 실제 객체에게 일을 토스한다.

→ 실제 객체 내부로 들어온 상태에서 processOrder()를 부르면, 프록시를 거치는 게 아니라 자바 실제 객체 자기 자신(this)의 메서드를 직접 호출하게 된다.

→ 결국 프록시가 끼어들 여지가 전혀 없어서 @Transactional 어노테이션은 무시되고 트랜잭션 없이 로직을 돌다가 데이터가 깨지는 장애로 이어진다.

호출이 프록시를 통과하지 않고 실제 객체 내부에서 자가 호출이 일어나면 프록시 기반의 스프링 부가 기능은 전혀 동작하지 않는다. 이를 해결하기 위해 아키텍처 계층을 분리해 외부 클래스에서 호출하도록 변경하거나, 구조를 재설계해야한다.

## 정리

- 프록시 패턴 - 실제 객체와 똑같이 생긴 인터페이스 뒤에 대리 객체를 세워, 실제 객체의 코드를 건드리지 않고 접근 제어 및 부가 기능을 삽입하는 패턴이다.
- 실제 객체는 순수 비즈니스 로직에만 집중하고, 권한 확인/로깅/캐싱/시간 측정 같은 인프라 관심사는 프록시 프록시 객체가 전담하여 책임진다.
- 우리가 사용하는 스프링 AOP와 @Transactional은 프록시 패턴을 프레임워크 수준에서 자동화를 둔 핵심 기술이다.
- 프록시는 오직 외부에서 관문을 타고 들어오는 호출 경로에만 제어할 수 있으므로, 내부에서 메서드가 메서드를 직접 호출하는 자가호출 환경에서는 무력화된다.
